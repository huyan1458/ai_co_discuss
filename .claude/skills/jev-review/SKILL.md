# 智能调度负反馈审查（jev-review）

目标：把每条 👎 还原成“模型看到了什么、为什么这么选、用户本来想要什么”，找出可以改进的问题与选项设计。报告只在对话中输出，不写文件；是否改 `runner/scheduler.mjs` 由用户决定。

## 1. 先读设计依据

读 `.dev/docs/Insight_决策模型使用经验.md`：场景表、全部经验和已有案例是判断的基准。再读 `.dev/docs/Ref_智能调度场景清单.md`：各场景（自由房路由、`@全体成员`、讨论插话、下一位发言人、下一轮）当前的题干、选项、阈值与提示版本，以及已知边界。已记录过的案例和已知边界不重复诊断，只说明是否复发。

## 2. 读取负反馈快照

本机站点默认 `http://127.0.0.1:8765`，回环访问即管理员。按页读取，`next_after` 非空时用它续读：

```bash
codiscuss api "/api/scheduler-feedback?after=0" --site http://127.0.0.1:8765
```

用户指定只看最近或某个编号之后，就从对应 `after` 开始。线上站点需要管理员登录，CLI 不带管理员会话，遇到 401 时告诉用户改在本机站点审查，不尝试绕过。

每条 case 的字段：

- `room_title`、`room_id`：来源房间（房间可能已删除）
- `should_be`、`note`：用户认为应由谁回答及说明，是“真实意图”的唯一依据；为空时如实写“未说明”，不替用户猜
- `snapshot.input.state`：发给模型的原文状态（房间、目标、近期消息、待处理消息）
- `snapshot.input.questions`：题干 `instructions` 与每个选项的 `description`
- `snapshot.detail`：模型选中项与各选项概率
- `snapshot.label` / `confidence` / `applied`：最终显示与是否执行
- `snapshot.context`：模型、阈值、提示词版本 `prompt`、包版本

`snapshot.input` 为 `null` 的是本功能上线前的判断，只能依据题干记录和概率做有限诊断，须注明。

## 3. 逐条诊断

对每条 case 依次回答，结论必须引用快照原文：

1. **该选什么**：按 `should_be`/`note` 对照场景表，自由房路由归入经验文档的 S 编号，讨论中的判断（`kind` 为 `round` 或讨论插话）归入场景清单的场景 3–5，都对不上时标记“新场景”。
2. **依据给到了吗**：判断所需的事实（点名、`reply_to`、谁在处理哪条）是否出现在 `state` 里；缺失则归因“上下文缺失”。
3. **选项是否冲突**：用户期望的选项与模型选中项的 `description` 是否语义重叠、例子是否把这条消息当成了判据；概率是否被两个选项分摊。
4. **题干是否误导**：`instructions` 的判断顺序或措辞是否把这条消息引向错误选项。
5. **阈值问题**：模型方向对（期望项概率最高）但被阈值挡下，记为阈值问题，并列出与阈值的差值。
6. **用户意图是否超出可判断范围**：上下文里本来就不存在依据的，归因“超出决策模型职责”，建议保持交给主持人。用户写在成员描述里的分工与擅长是可用依据（已确认接受按专长分派），不算揣测。
7. **值不值得进固定场景集**：对照 `tests/jev_cases.json` 判断，结论为“建议入集 / 不入集”并给理由。须同时满足才建议入集：
   - 期望答案明确：`should_be`/`note` 能确定唯一正确选项（或明确可接受的备选）；用户未说明且从原文也定不下来的不入集。
   - 有代表性：用户的说法会反复出现，或落在两个选项的边界上；只在这个房间才成立的偶发情况不入集。
   - 不重复：已有用例覆盖同一判据时只说明“复发，见 Sx”，不新增；只在措辞明显不同、已有用例测不出时才补。
   - 能脱离原房间复现：判断依据能用几条前文和成员信息表达，不依赖长篇原文。

   建议入集时附一条可直接粘贴的用例草稿，字段与该文件同场景的已有用例一致（`id`、`scene`、`note`、`message`、`context`、`expect` 及场景所需字段）。`tests/` 会进 Git，草稿须把真实对话改写成最小场景：换掉人名以外的项目名、路径、业务内容与任何隐私，只保留决定判断的措辞与结构，不照抄原文。

归因只能是：上下文缺失 / 选项描述重叠或误导 / 题干误导 / 阈值 / 超出职责 / 证据不足。不确定时写“证据不足”，不编原因。

## 4. 输出报告（对话中）

- **概况**：审查范围（`after` 区间、条数）、按提示词版本与归因的计数。
- **逐条**：房间标题、待处理消息原文、模型选择与概率、用户期望、归因、引用的输入片段、入集结论（建议入集时附用例草稿）。
- **共性问题与修改建议**：同一归因出现多次时合并；给出具体要改的题干或选项措辞（新旧对照），并说明改后须升提示版本（自由房 `ROUTE_PROMPT_VERSION`，讨论 `DISCUSSION_PROMPT_VERSION`），把确认了期望答案的案例补进 `tests/jev_cases.json`，再运行 `node tests/jev_eval.mjs --baseline tests/jev_baseline.json` 确认没有其他场景翻转后上线（评测会把文本发给模型服务商并计费，须用户同意）。
- **下次续读位置**：本次最后一条的 `decision_id`。

不做：修改代码或提示词、调用决策模型、删除或改动反馈数据、把单条样本直接写成定论、自行写入 `tests/jev_cases.json`（入集由用户确认后另行修改）。
