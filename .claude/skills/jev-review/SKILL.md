# 智能调度优化（jev-review）

目标：让智能调度少派错人、少让主持人白转手。证据有两类：房主的 👎（真实意图）和回归评测（改动是否让别的场景翻转）。

## 先读（每种模式都要）

- `.dev/docs/Insight_决策模型使用经验.md`：定位与要求、两种判断方式（引导 / 稳定）各自的评判标准、阈值的定法、已有案例。判断“该不该改、改成什么样”以它为准。
- `.dev/docs/Ref_智能调度场景清单.md`：各场景当前题干、选项、阈值、提示版本、回归基线、已知问题与试过并撤回的改法。已记录的不重复诊断，只说明是否复发。
- `.dev/docs/Ref_技术细节.md`“智能调度（可选）”：执行入口、决策记录字段、回归评测命令与参数。

## 选模式

按用户的话选；没说清时做“审查反馈”，结尾建议下一步。

| 模式 | 典型说法 | 改动 |
|---|---|---|
| 审查反馈 | 看看最近的负反馈 | 只读 |
| 回归评测 | 跑一轮回归、两种模式比一下 | 用户要求时才更新基线 |
| 优化 | 优化引导模式、把这条加进回归集、门槛设多少 | 代码、用例、测试、基线、文档 |

回归评测与优化会把用例文本发给模型服务商并计费，用户选择这两种模式即视为同意，报告里写明调用次数。任何模式都不提交、推送或部署，除非用户另行要求。

## 审查反馈

1. 读快照：`codiscuss api "/api/scheduler-feedback?after=N" --site http://127.0.0.1:8765`，`next_after` 非空时续读；线上站点 401 时请用户改在本机审查。
2. 按 `snapshot.context.mode` 分组，对每条说明：用户期望（`should_be` / `note`，为空写“未说明”）、模型选了什么及各选项概率、实际执行是否派错人、模型看到的 `input` 里缺了什么或哪里引偏、是否值得入集（附去隐私的最小用例草稿）。结论引用快照原文，不确定写“证据不足”。
3. 报告：概况（范围、按模式与版本计数、派错与退回主持人条数）→ 逐条 → 共性问题与修改建议（新旧措辞对照）→ 下次续读的 `decision_id`。

## 回归评测

1. 两种模式各跑一遍 `tests/jev_eval.mjs`（`--mode`、`--repeat 3`、对应基线，见技术细节），全量较慢时放后台。
2. 报告：各场景 PASS / WEAK / FAIL、派错人清单、两种模式结果不同的用例、相对基线翻转的用例。

## 优化

改提示词前先读 `/prompt-design`（提示词设计原则）。

1. 用回归评测建基准，列出要改善与要守住的用例。
2. 先定位原因（消息变体或单因素探针），再改；一次只改一个因素，每步 `--repeat 3` 对比，按经验文档的标准决定保留或撤回。
3. 按需要的步骤：
   - **扩充用例**：写进 `tests/jev_cases.json`（最小化、去隐私；有合理备选用 `accept`），`JSON.parse` 校验后两种模式各跑新用例。
   - **调门槛**：用评测结果按经验文档的方法模拟各档位，再改 `scheduler_thresholds`。
   - **新的执行去向**：属于产品改动，网站两套后端同改并补测试，先向用户说明范围。
4. 定稿：升对应提示版本，更新并运行单元测试（`tests/test_runner.mjs`、`tests/test_api.mjs`，涉及后端时加 `tests/test_free_room.py`、`tests/test_pages.mjs`），更新基线，同步场景清单（原文、版本、结果、试过并撤回的改法）与经验文档（只写可复用的教训）。
