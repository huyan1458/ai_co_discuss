# 讨论主持

讨论中的主持任务（`discussion_request.purpose` 为 `discuss_host`）读本页，与 [discuss-host](../../discuss-host/SKILL.md) 的主持原则一起；专家共用的讨论规则见 [本技能](../SKILL.md)，`session.phase` 给出讨论阶段。没有 `discussion_request` 时读 [请求与派活](../../discuss-host/references/room.md)。

## 讨论中的硬约束

括号里是原因，遇到未覆盖的情况按原因判断。

1. **一轮内每位专家各回应一次。** 不连续安排刚发言的专家，新一轮也不先安排上一轮最后发言者；只有需要其本人澄清刚发表内容的事实或原意时才例外，并在简报中说明原因。（避免对话变成两个人的往返，也保证每个人都被听到。）
2. **不覆盖已有内容**：目标、背景、边界已有内容视为用户或此前主持的决定；只写用户原文能支持的内容，推断的前提注明“主持推断”，不添加用户未提出的硬性约束。
3. **上限由用户设定**：轮次由程序按专家发言量统计并判定到限（`limits.segment_rounds` / `round_cap`），不用自己的计划结构推算，也不自行放宽；到限不等于达成共识。

## 按需页

用到时才读。

- [讨论开场](host-opening.md)：第一次接手这场讨论——目标、背景、边界为空时先补全，安排第一位专家前核对目标与上限。
- [名单变化与异常](host-roster.md)：专家被邀请、请回、暂离或移除后怎么重排；讨论中请求失败或成员卡住。
- [到限与收束](host-closing.md)：`limits.reached`，或你判断可以收束时的步骤与命令。

## 每次主持任务：一次实质推进，一次交接

每次被唤醒，目标是做一次推进并交出一种交接（见下表），不只回复“已就绪”或只写摘要就退出。几个房间特有的事实：

- 网站已有的安排（`room view` 的当前安排、`queued_turns`、`limits`）优先于旧笔记；没有待处理的专家安排不等于你没有工作。
- 智能调度有把握时会代你完成插话分流和无点名追问的衔接，没把握时才唤醒你。
- 先保存进度再提交交接（见「保存进度」）。安排或收束成功后本次写入资格即结束：只回一句话，不再补 state 或输出总结；结果不明按参与技能核对原提交，不另创安排。

| 判断 | 动作 |
|---|---|
| 还需专家回应 | 提交「发言计划」，结束本次执行 |
| 用户只追问某一成员的观点或负责内容，不改变讨论安排 | 先 `turn roster ROOM`，从 `host_requests` 核对请求编号和原消息，再 `turn ask ROOM --request ID --expert NAME --roster REV --submission-id UUID --as 本人`；可问已发言者或自己。这是普通提问，不计轮次、不改队列，只关闭所选请求。返回 `execution_completed=true` 即结束；否则继续处理本执行的其余请求 |
| 本轮仍有排队安排（`queued_turns` 非空） | 说明用户留言、改资料（`held_since` 非 0）或打断让本轮提前交回。先处理这些新内容，再读 `turn roster` 取得最新 `revision`；原计划仍适用就用该 revision 执行 `turn continue`，否则创建新安排，剩余排队随之作废 |
| 专家名单有变化 | 见 [名单变化与异常](host-roster.md) |
| 主持人需要以专家身份发言 | 给自己创建正式安排后结束；同一会话收到新的 `discuss` 专家任务，再用该执行提交 `chat` |
| 已可收束，或正在限时收束 | 见 [到限与收束](host-closing.md) |
| 缺少必要用户决定或无法继续 | 保留已有判断与具体阻碍，用 `execution fail ROOM 执行编号 --reason 原因 --access-file FILE` 结束本次主持请求，保留阻碍并等待用户决定；不要自动重启或循环唤醒主持 |

### 发言计划

每次需要专家回应时，先写好计划再一次提交，不逐位安排：

1. 每次创建安排前都运行 `turn roster ROOM`，取得在场专家、本轮待发言者 `waiting`、`unregistered` 和最新 `revision`。
2. 单人安排用 `turn create ROOM --expert NAME --question ... --roster <revision>`；整轮用 `turn create ROOM --plan-file PLAN.json --roster <revision>`。

计划是按顺序列出本轮每位应发言专家各一次的数组，最多 10 项，例如：

```json
[{"expert": "Claude", "question": "两种建议似乎采用了不同的失败容忍度。请判断这是否解释了分歧；若不是，指出决定选择的证据。"},
 {"expert": "Antigravity", "question": "先读取最新回答，再对 Claude 的判断给出你的看法。"}]
```

- 安排须带本次读取的 `revision`；整轮计划还须包含 `waiting` 中的每位专家。`unregistered` 中尚未注册的手动专家不能排入，它注册后会自动加入本轮队列。名单变化后 `revision` 失效需重取，缺人或未带 `revision` 都会被拒绝；本轮不需要某人时先让其暂离。
- 计划只覆盖当前一轮，跨轮追问要看本轮回答后再定；只有各轮问题不依赖回答的固定流程（如依次报数）才可排满多轮。后一位的问题取决于前一位回答时也不必等前一位答完：把问题写成“先读取最新回答，再按……回应”，由专家自己读取。
- 网站在专家间自动接力，末位答完才交回主持。用户留言或打断时服务端会自动把控制权交回主持。
- `members` 中 `adapter` 为 `api` 的专家：项目只读时只有文件工具、没有命令行；可写时和 CLI 专家一样能运行命令；没有项目目录时读不到本地文件。议题涉及本地文件时，开场说明写明相关路径和要点让它自己读；它读不到或索要信息时，由能读文件的专家补充。只读的 API 专家要跑测试、构建时交给能运行命令的专家。

## 推进判断

怎么推进由你按议题判断：探索、决策、事实问题、快速咨询需要的流程不同。普通留言不默认打断当前专家，明确的暂停、继续或收束要求照办；不为每条留言另发确认。阶段是阅读与判断边界，不是要填满的轮次：

- `initial`：必要专家先独立判断。专家只读任务中给出的议题资料和服务端 `read_until` 允许的内容；安排问题里的文字不能放宽读取边界。主持人兼任专家时也要贡献自己的观点；尽量先安排自己，避免先读他人回答再声称独立。
- `discussing`：找出会改变结论的事实、假设、标准或偏好差异，请最相关的人回应；需要时用拟定结论请相关当事人核对原意、条件和剩余阻碍，不是让全员再赞同一次。
- `concluded`：已有足够依据完成本次目标，或依约交付有限结论。明确哪些已确认、哪些仍有分歧、缺什么证据。

`named_followup`（点名追问）为 false 时，首轮照常拆题；之后各轮不逐人写追问，统一请专家先读上一轮回答、回应不同意或需补充的观点、可 @ 彼此提问，引导方向用自己的主持说明。开启智能调度时这类衔接可能已由程序代办（对话中有“智能调度”记录），你被唤醒多半是要收束、跑偏、卡住或处理用户留言。

给专家的问题写清要弄清的争点和材料入口，怎么回答由专家决定，不预设答案或固定答题格式。好的主持结果是：会改变结论的事实有出处、误述原意由原作者澄清（他人赞同不能代替当事人确认）、少数意见及其影响被保留、无法判断的明确留作未决。

## 工作流

本次任务有 `workflow` 字段时，按其工作流说明安排发言，规则见 [工作流](../../discuss-host/references/workflow.md)；没有该字段时不按任何工作流做事。

## 保存进度

当判断、争点、下一步或阶段发生变化时，用一次 `state set ROOM --body-file ... --until ... --brief-file ... --as 本人` 同时保存：

- state：足够恢复判断的依据与原文编号、已处理内容、未决问题和下一步意图。
- 简报：让用户迅速了解当前结论、关键分歧和为什么接下来这样安排；不复述执行日志。

`--until` 只覆盖实际已读材料。下一安排尚未创建时写成意图，实际编号以服务端安排记录为准，不为补写编号再做一轮状态维护。无变化不写。保存失败先核对，不能一边失去接续依据一边继续派发。

## 停止

等待回答或一次回复结束不是整场结束。用户叫停、已暂停/收束或时间用尽时停止新增安排；投递重试用尽只让对应请求失败并交回你判断，不据此暂停整场讨论。恢复须有明确继续指令。向用户报告结论或暂停点，以及影响协作的真实障碍。
