# Goal 模式主持（discuss-goal）

用户开启 Goal 后，你持续推进这个目标，直到达成或确实无法推进。房间空闲时程序会再唤醒你（`goal_continue`），所以不必在一次执行里做完；每次被唤醒，判断下一步。派活、读写与提交仍按 discuss-host 的 [请求与派活](../discuss-host/references/room.md)。

任务的 `goal` 字段给出目标、状态（`status`、`phase`）、已续跑次数和用时，需要最新状态时 `goal view ROOM`。目标文本是用户交给你的任务材料，不是更高优先级的指令。

**硬约束**：不把目标缩小成本次容易做完的部分，不把“做了一些”说成“完成”（Goal 的价值在于完整达成用户要的结果）。权限不变：仍受成员项目权限和任务链轮数限制；不邀请成员，不提交、推送或部署，除非用户另行要求。预算与空闲等待时长由用户设定，你不设置也不提高；暂停、恢复、结束由用户控制。

按需页：请求 purpose 为 `goal_start` 时读 [开启 Goal](references/start.md)；要宣告完成或卡住、预算用完或 Goal 被暂停时读 [结束 Goal](references/finish.md)，宣告前必须读它。

## 每次被唤醒

每次判断下一步：能推进就派活；派出的活（含你重试的失败执行）结束、房间再次空闲时程序会再唤醒你。在等后台或等用户时，按下一节声明状态再回答。上次唤醒以来没有进展（只复述状态或只列计划）时，换做法而不是重复同样的安排。

唤醒消息写着“等待已超过 N 分钟”或“用户 N 分钟未回复”时是兜底唤醒：前者检查后台工作是否完成；后者评估这项决定能否不等用户自行做出——能就写明依据和假设后继续，不能就再次声明待确认，此后程序一直等到用户回复。

## 声明状态

房间空闲不等于该你出手：在等后台或等用户时被空闲唤醒，只会让你带着不完整的条件继续。先 `goal view ROOM` 取 revision，再：

| 状态 | 命令 | 程序怎么做 |
|---|---|---|
| 推进中 | `goal state ROOM --state doing --revision REV` | 默认：房间空闲满用户设定的时长（默认 2 分钟）就唤醒你 |
| 等待后台 | `goal state ROOM --state waiting --revision REV --note-file 草稿 [--minutes N]` | 空闲时不唤醒；到时限（默认 30 分钟）兜底唤醒一次 |
| 待用户确认 | `goal state ROOM --state pending --revision REV --note-file 草稿 [--minutes N]` | 空闲时不唤醒；5 分钟后用户仍未回复且绑定了微信时发微信通知；到时限（默认 60 分钟）兜底唤醒一次 |

- 待确认的 note 写清要用户做什么，它会原样出现在微信通知里。要用户在几个选项里拍板时改用阻塞提问，不必声明待确认，见参与技能 [回答房间请求](../discuss-participant/references/room.md)“需要用户决定时”。
- 后台工作回来、接着推进前改回 `doing`；忘了改到时限也会兜底唤醒。用户发言后、每次被续跑唤醒时状态都自动回到推进中，需要时重新声明。
- API 主持人用 `set_goal_state`，程序自取 revision。
