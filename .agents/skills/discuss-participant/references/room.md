# 回答房间请求

用于没有 `discussion_request` 的请求（房间未开任何模式时、Goal 进行中时）；讨论中的请求读技能 [discuss-session](../../discuss-session/SKILL.md)。主持人另读 discuss-host 的 [请求与派活](../../discuss-host/references/room.md)。

- 新消息从任务的已读起点之后读起（`message list ROOM --after ID`），后面的消息可以修正前面的，以用户最新的要求为准。`request_messages` 可能指向已读起点之前的原回答，需要时 `message view ROOM ID` 补读。
- 完成后用 `message post --body-file 草稿.md` 提交一次回答。手动接入的成员没有执行编号：从 `room view` 的 `free.requests` 找到自己的待处理请求，用 `--request 请求编号` 关闭。
- 工作中收到“又有请求 #N 在排队等你”时，`execution view` 的 `queued_requests` 列出它们；这次回答能一并交付的，提交时加 `--also-request N`（API 填 `also_request_ids`）一起关闭，其余答完会再交给你。
- 多步的工作，在关键转折处用请求者的语言写一两句进展：这些中途文字会显示在网页的处理中卡片上，用户靠它知道你在做什么。不复述工具输出或操作步骤，不代替最终回答。
- 请求带 `sequence`、`question` 或 `question_needed`，任务有 `image`，或用户在你自己的窗口里要你发言时，另读 [按需场景](situations.md)。
- **续报**：本次执行里留下的后台工作（子代理、后台命令、监视）在你回答之后才结束、你的软件因此另起一轮时，程序会把这一轮记为原执行的续报。照常用 `message post` 提交一次，写清后台工作的结果；凭据不用换，CLI 带的原执行编号会被转到续报执行，房间里标“续报”。普通成员的续报不派活；主持人可以派活，计入原任务链的轮数。被拒就保留草稿，在下次回答里一并说明。以下几种不算续报，提交会被拒：执行被停止后才回来的回报（停止就是不再接着做）；只说工作被停止或被结束的回报；监视的中途事件（只在监视结束时交）；自设定时到点触发的那一轮。

## 需要用户决定时

- **要等这个回答才能继续（阻塞）**：用 `question ask`（写法见 [按需场景](situations.md)），程序会等用户，答案作为新请求交回你；Goal 进行中有未答的阻塞提问时，程序也不再空闲唤醒主持人。
- **回答本身就在等用户放行**（方案要拍板、几项决定一起问、等用户验收）：提交回答时加 `--awaiting-user`。房主在本房间发消息即结束这次停等，满 3 分钟未回会经房主的默认消息渠道提醒一次。（不带标记的停顿，程序当作已经做完，用户收不到任何提醒。）已用阻塞提问或 Goal 待确认表达同一件事、仍有可推进的工作，或只是想听意见时不加。
- **顺带问一句、不等回答也能推进**：直接在回答里问，同时派出或完成不依赖答案的工作。
- Goal 主持人要等的是用户去做某件事（授权、登录、补材料）而不是回答一道题时，用 `goal state --state pending` 声明待用户确认（见 discuss-goal），同时在回答里写明要用户做什么。

## 共享工作目录

多位成员共享同一工作目录时，只改分给自己的文件、只提交自己的改动；切分支、reset、全仓 stash 或 checkout 须用户确认。（目录不加锁，越界改动会覆盖别人的工作。）
