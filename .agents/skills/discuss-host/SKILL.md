# 讨论主持（discuss-host）

把用户的议题推进为有依据的判断，保留有价值的分歧与未确认事项。**主要工作是理解论证、发现影响结论的争点、提出有效追问；流程只用于可靠交接这些工作。**

主持人同时调用 [discuss-participant](../discuss-participant/SKILL.md)。阅读、署名、发言权、可靠提交和执行凭据统一由参与技能定义，本技能只补充主持决策与交接。编辑或评审技能不启动讨论。

## 先判断讨论需要什么

先明确用户想解决的问题、背景、约束和合格结果；沿用已有共识，只询问阻碍推进的缺项。探索可以保留多个方向，决策需要比较标准，事实问题需要可核验的证据；快速咨询不必套完整的全员流程。

用户提出目标、约束与偏好，并作出最终决定；主持人负责理解用户意图、判断对讨论的影响并安排后续发言。安排下一位专家或收束前，先处理尚未处理的用户留言，结合上下文决定直接回答、调整问题、请相关专家回应或改变方向。意图清楚就推进，只在影响判断的关键歧义处确认，不只转发留言。用户的倾向不等于已验证事实，参与者仍应独立判断并指出矛盾与风险。

原生定时与事件驱动均遵循此约定，分别在下一次检查或主持执行中处理；普通留言不默认打断当前专家，明确的暂停、继续或收束要求按现有规则执行。通过后续发言、主持简报或总结自然说明用户意见如何被处理，不为每条留言另发确认回执。

默认先形成必要的独立观点，再围绕关键分歧深入讨论，按需复核并总结。阶段是阅读和判断边界，不是需要填满的轮次：

- `initial`：必要专家先独立判断。主持人兼任专家时也要贡献自己的观点；尽量先安排自己，避免先读他人回答再声称独立。
- `discussing`：找出会改变结论的事实、假设、标准或偏好差异，请最相关的人回应。一轮内每位专家各回应一次，轮次以此计数；不连续安排刚发言的专家，新一轮也不先安排上一轮最后发言者。只有需要其本人澄清刚发表内容的事实或原意时才例外，并在简报中说明原因。
- `reviewing`：仅在需要时，用拟定结论请相关当事人核对原意、条件和剩余阻碍；不是让全员再赞同一次。
- `concluded`：已有足够依据完成本次目标，或依约交付有限结论。明确哪些已确认、哪些仍有分歧、缺什么证据；到限不等于达成共识。

追问应说明真正需要弄清的争点及材料入口，给专家自主质疑前提、发现遗漏和改变观点的空间，不预设答案或固定逐项答题格式。例如：“两种建议似乎采用了不同的失败容忍度。请判断这是否解释了分歧；若不是，指出决定选择的证据。”

意见相同不等于事实已验证，意见不同也不必投票决定。核对会改变结论的数字、出处与适用条件，区分实测、外部声称、估计和建议。误述原意时请原作者澄清；另一人的赞同不能代替当事人确认。保留少数意见及其影响，不为了收束抹去限制，也不为凑轮次制造争论。重复立场时缩小争点或补有区分力的证据，仍无法判断就明确保留未决。

## 定位、模式与上限

当前实际会话承担主持，不另建调度聊天。沿用用户指定的房间和运行方式；新讨论尚未选择时，只确认“全自动讨论 / 手动复制冷启动”。自动任务已表明用户启动意图，无需再次确认。

未指定房间时，先用 CLI 建房并保存目标、背景、参与配置和上限，核验后再接入专家。全自动要求主持和专家均具备本地 CLI 读写能力；配置完成后依据用户的启动指令运行，创建房间本身不代表已启动。在线只读专家使用手动接入分工，不静默转换模式。

新建讨论时，将用户请求完整保存到房间独立的“用户原文”字段（CLI 使用 `--user-request-file`），不改写或概括；“背景”只保存补充材料，其余主持流程照常。原文超过该字段 4000 字上限时，将完整原文按参与技能保存为开场主持消息，“用户原文”保留原文消息链接，不截断原文。

工具入口、站点、项目与 cwd 的定位遵循参与技能。新建会话可指定所属项目及 cwd，也可缺省；已有会话不靠提示词迁移目录。仅在首次配置或启动自动程序时查阅仓库 `docs/deployment.md` 与 `docs/cli.md`，不把安装操作混入每次讨论。

每次接手先读 `room view`，用其中的阶段、当前安排、`limits` 和运行状态恢复现场，再按需补读 state 与有关原文。网站已有的安排优先于旧笔记；没有待处理的专家安排不等于主持人没有工作。

遵守用户设定的轮次、总时长、单次执行及到限方式，不自行放宽。轮次以服务端 `completed_rounds` 为准；暂停、准备与收束期间不计时。到限而尚未进入收束时，用 `room limits ROOM --check --as 本人`（受保护写入附本次 `--access-file`）处理：

- 返回暂停就停止；自动执行若换代，结束旧执行，等待新任务。
- `limits.closing=true` 且本次执行仍有效时，只根据已有材料总结，不再安排专家。预留时间包含在总时限内，来不及完成就保留未决，不谎称收束。

## 自动主持：一次实质推进，一次交接

收到自动任务后，按参与技能进入本次执行；若当前调用已成功进入，不重复认领。不创建原生定时，也不手动通知已配置的本地专家，通知程序负责后续交付与续租。

阅读新增的相关回答、用户约束及必要原文，判断下一步是追问、补证、复核还是收束。不要只回复“已就绪”或只写一段摘要就退出；本次执行需要以以下一种结果交接：

| 判断 | 保存与结束边界 |
| --- | --- |
| 还需专家回应 | 先保存本次判断与下一步意图，再持有发言权创建一个正式安排；创建成功即结束本次执行。 |
| 主持人需要以专家身份发言 | 给自己创建正式安排后结束；同一会话收到新的专家任务，再凭新资格发表 `opinion`。 |
| 已可收束，或正在限时收束 | 先发表有原文依据的最终 `moderation`、保存 state 与简报，最后设为 `concluded`。 |
| 缺少必要用户决定或无法继续 | 保留已有判断与具体阻碍，用 `execution fail` 暂停，向用户说明需要什么。 |

创建安排、完成收束或执行失败会结束本次写入资格；此后只允许回读核验，不再补 state、回执或归还已交接的发言权。是否完成以网站业务结果为准；结果不明按参与技能核对原提交，不另创安排。

## 保存有用的进度

当判断、争点、下一步或阶段发生变化时，用一次 `state set ROOM --body-file ... --until ... --brief-file ... --as 本人` 同时保存：

- state：足够恢复判断的依据与原文编号、已处理内容、未决问题和下一步意图。
- 简报：让用户迅速了解当前结论、关键分歧和为什么接下来这样安排；不复述执行日志。

`--until` 只覆盖实际已读材料。下一安排尚未创建时写成意图，实际编号与状态由服务端安排记录提供；恢复时两者对照，不为补写同一个编号再做一轮状态维护。无变化不写，已在当前上下文的材料不反复全文读取。保存失败先核对，不能一边失去接续依据一边继续派发。

最终总结必须另以主持消息留档，简报不能替代它；结论、不同意见、重要条件与未验证影响按议题组织，不强制固定栏目。用户要求独立报告时再调用仓库的 discuss-report，报告不表示建议已获采纳。

## 手动兜底与停止

**仅在用户选择手动模式、需要在线专家转交或处理已有原生任务时**，读取 [手动接入与持续主持](references/manual.md) 对应部分。自动讨论不加载这份操作细节。

等待回答或一次回复结束不是整场结束。用户叫停、已暂停/收束或时间用尽时停止新增安排；自动任务的失效与失败遵循参与技能，手动模式清理本话题的原生任务。恢复须有明确继续指令。向用户报告结论或暂停点，以及影响协作的真实障碍，不索要全员启停回执。
