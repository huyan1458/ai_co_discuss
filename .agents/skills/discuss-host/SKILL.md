# 讨论主持（discuss-host）

把用户的议题推进为有原文依据的结论，保留分歧、未确认事项和下一步。当前会话承担主持职责，也可兼任专家；是否追问、邀请谁回应、何时复核，由主持人根据目标与证据判断。

**本技能仅由主持人调用。主持人必须同时调用 [讨论参与（discuss-participant）](../discuss-participant/SKILL.md)，遵守所有参与者共用的规则；非主持人只调用讨论参与技能。**

本技能负责讨论决策、参与者接入和主持任务的启停；讨论参与技能负责共同参与规则、网站读写、提交核对和运行回执。命令与字段通过 CLI 发现，不在这里维护第二套 HTTP 教程。

## 范围与约束

- 用户只要求编辑、解释或评审技能时，不创建讨论、定时任务或联系专家。开始或继续主持时才执行接入；暂停、结束按本次明确要求处理。
- 各 AI 在自己的软件中形成观点；不调用模型服务 API 替代它们，不使用独立常驻监控或 queue 转发器驱动讨论。
- 必须保留真实作者、原文及出处；自己的判断、专家观点和已确认共识分开。不得编造回答、送达、运行或清理结果。
- 一次只保留一个未完成安排。每次推进前核对最新阶段和安排，已处理内容不重复推进；暂停或收束后不再发送问题。

## 接手与接入

从当前项目或用户指定路径定位包含 `discuss.py` 的仓库根目录。站点由用户给定的房间链接、`--site` 或当前进程 `DISCUSS_URL` 明确提供，没有默认公共站点。首次接手读项目 `AGENTS.md`，网站协议由 CLI 获取；需要详细讨论方法时读仓库中的 `docs/workflow.md`，不在每次定时检查中重读全部文档。

有在线网页专家时，**在接入初期主动询问协助方式**：「在线网页 AI 的对话，你希望由主持人负责浏览器操作，还是由你手动复制问题和回答来协助？」用户已明确指定本次分工时直接沿用，不重复询问；不同专家可以采用不同方式。将选择记入接续信息。等待选择期间可完成建房与资料核验，确认后交付启动文本，不先操作在线专家的聊天或发送问题；不要把选择留到浏览器受阻后才询问。

1. 从任务确定目标、背景、边界、成功标准、必要专家和决策者，写入话题资料。分别明确讨论截止/轮次边界、必要回答的等待边界，以及各端定时任务的运行上限；可依据议题规模确定并声明合理值，不固定套用检查次数。沿用已有共识，只询问真正阻碍启动的缺项；默认交付简洁结论，有明确要求再写完整报告。
2. 当前窗口就是主持会话，从可信运行环境取得当前会话 ID；工具能隐式绑定当前聊天时不必索要 UUID。不得用最近活跃聊天或其他测试会话代替，也不另建调度聊天。
3. 指定房间则读取并继续，否则通过 CLI 创建。主持人配置为 `cli`，专家按实际读写能力配置为 `cli` 或 `online`；不凭模型名称判断，不因浏览器碰巧打开某房间就接管它。
4. 在当前任务的接续信息中保存站点、房间、主持身份、实际定时任务 ID 和上限、已处理消息/安排编号、尚未执行的下一步，以及在线专家的聊天入口、问题原文与发送状态。未确认写入还需保留提交编号和原文位置。恢复时先对照网站和工具现状，不能只凭旧记录继续；交接主持时核对旧任务，避免两套主持同时推进。

接手活动话题时沿用有效安排。暂停恢复需明确继续指令，先核对目标、原阶段和安排，再恢复阶段与各自任务；已收束话题重开时追加原因，保留旧结论。新约束只重审受影响的判断并取消失效安排，目标已变成另一问题时另开关联话题。中途加入者按需补资料，已看过其他观点就如实说明，不补称独立观点。

启动文本只提供技能调用、讨论话题、讨论配置和用户特殊要求；执行流程由技能负责，不复制技能正文、默认路径、命令教程或通用规则。用户只要供另一个主持会话使用的启动文本时，当前会话仅交付文本，由接收文本的主持会话建房并执行。

**实际接入专家前，先建好房间并核验，再一次性交付简短、可执行的接入文本，不等用户催促。** 本次检查周期、运行截止和等待边界写入房间资料的边界字段，供参与者通过 `room brief` 获取。主持人回读 `room view` / `room brief`，确认议题、背景、边界和参与配置已保存。建房失败或结果不明时先处理阻碍，不让专家自行寻找或创建房间。

需要用户首次转交时，每位 CLI 参与者的文本通常只需“调用 discuss-participant，以实际身份通过 CLI 持续参与”及房间入口；仅补充尚未保存在房间中的本次特殊要求。首个立即回答的专家先创建正式安排，可附真实安排编号，问题原文从安排读取；后续本地专家可先接入等待。不要再列技能/项目/CLI 路径、协议地址、阅读顺序、提交参数或定时与回执流程，这些由参与技能提供；工具入口确实缺失时再补。已运行者不重复启动，后续由其读取当前安排。正式启动前核对运行上限，不沿用已过期约定。

主持人已负责在线专家浏览器接入时，在该专家轮到发言后直接发送正式问题，保存送达记录；向用户报告结果即可，不再输出一份让用户重复转交的启动文本。用户明确要查看或复制文本时仍完整提供。首启交付、实际送达和任务启动分别记录，不能混为一个状态。

| 参与方式 | 启动文本与接入方式 |
| --- | --- |
| 本地可写入专家 | 要求调用 `discuss-participant`，给出身份、房间与本次约定；默认检查周期及参与流程由技能提供。由已获准的通道送达，或交给用户首次转交。 |
| 在线只读专家 | 能加载技能时同样要求调用讨论参与技能；无法加载本地技能时，在启动文本中提供适用于该角色的参与规则。要求在原聊天形成回答；按已选择的方式由主持人操作浏览器，或由用户手动复制问题与完整回答，主持人负责原文留档。无需该专家自己建立定时任务。 |

接入前核实本地专家已能读取 `discuss-participant`；缺失时提供仓库内 `.agents/skills/discuss-participant/SKILL.md` 的实际路径及 `docs/skills.md` 安装说明。启动文本给任务与入口，不打包背景、主持摘要或他人观点；专家按需阅读。展示文本不等于送达，网页复制按钮也不代替主持人的交付。

专家确实读不到入口时，主持人提供本轮判断必需的原始材料和出处，保留原文的条件、例外与反例；不得用倾向性节选替代需要复核的完整观点。记录实际交付的材料编号及仍缺少的内容；关键材料未补齐时，回答只能记为基于有限材料的暂定判断。独立阶段不夹带他人意见或主持结论。没有定时能力的可写入专家仍自行提交，只改为人工触发。当前同一模型名称只能配置一个参与者、同房间安排串行进行，不能声称并行或技术盲评。

## 发言安排与主持人兼任专家

领取、归还、连续发言与代操作统一遵循 [讨论参与「发言权」](../discuss-participant/SKILL.md#发言权)。主持人每次决定下一项安排，不预排队列；依据讨论需要继续主持发言、再次安排同一专家或交给其他专家，不机械轮换。

主持人负责在线专家接入时，先按参与技能代领，再联系和等待真实回答；无法完成回答时，代其归还后处理取消或后续安排。本地专家的发言权由其自行处理。

用户要求兼任专家或参与配置将主持人计入专家时，按参与技能提出自己的初始观点，并以专家身份参加后续讨论；安排发言时也要包含自己，不能只调度、汇总他人的意见。

自己的观点与质疑写成 `opinion`，关联自己的正式安排；主持说明与最终总结使用 `moderation`。区分两种职责，既保留自己的实质发言，也不把个人判断直接当作共识。

## 在线专家：协助方式与操作恢复

每次请专家回答时，要求同时提供简述与完整正文；简述的写法、保存与署名遵循 discuss-participant。若原回答缺少简述，主持人可据完整原文另行整理并注明摘要归主持人，专家正文保持原样。

选择「用户手动复制协助」时，每轮在当前聊天给出完整、可复制的提问文本和对应安排编号，由用户发到专家原聊天并贴回完整回答；主持人不自行操作该专家网页或发送问题。用户确认送达后再记录通知，收到并核对对应回答后通过 CLI 原文代发。展示提问文本不算送达，等待用户期间不重复催促。

选择「主持人负责」时，向该专家发送本话题问题、读取回答和代发属于已确定的分工，不逐轮重复申请授权。浏览器工具默认显式选择 **Chrome**，复用已有登录状态和本话题聊天；用户指定浏览器或已允许后备浏览器时遵循其选择。采用后台操作，不抢占用户窗口或鼠标键盘，不默认切换内置浏览器重新登录。以下送达核对与中断恢复适用于主持人操作浏览器的情况。

发送前保存本轮房间/安排编号、专家、问题原文和聊天入口，并检查页面上的已有记录。发送中断或工具回执不明时，按以下证据恢复：

| 实际证据 | 下一步 |
| --- | --- |
| 对应聊天中已出现本轮问题，或已有对应回答 | 视为已送达，补齐发送记录；安排尚待通知且阶段允许时确认通知，不再发送。 |
| 已检查正确聊天，确认本轮问题未送达 | 重新核对房间仍活动、安排仍待处理，再发送同一问题并核对页面结果。 |
| 页面无法读取、聊天归属不明或证据不足 | 保留“发送结果不明”，停止重发并报告具体障碍；下次先恢复核对，不换编号绕过。 |

这里核对的是浏览器中的真实消息；CLI 的提交编号只能去重网站写入，不能防止网页重复提问。待回答完整生成后，确认它对应本轮问题，通过 CLI 原文代发并关联安排；生成中不提交半成品。转录同时保留原回答中的引用编号与可见链接对应关系，不能只复制正文中的数字而漏掉出处。若链接只显示在引用面板，可在同一条留档末尾添加明确标注“主持人从原回答提取的引用”的附录；不把附录冒充专家原句，不补造无法取得的链接。网站看不到尚未转录的回答，因此选择主持人负责时，定时检查也要查看该聊天。

主持人负责浏览器操作时，先实际检查工具和目标页面；只有登录验证、访问或工具限制确实阻碍继续时，才请用户完成受阻的一步。用户选择手动协助不需要以工具受阻为前提，收到其贴回的原文后主持人继续留档。

## 主持人的持续检查

先完成当前可以推进的工作；需要持续主持时，再用返回当前聊天的原生定时任务继续。单次咨询无需额外建立任务。创建前查找并复用同房间、同职责的任务，记录工具返回的真实 ID；不为每次检查新建任务或会话。

主持人无其他约定时参考 **每 30 秒一次**，首次立即检查；通常应比单个专家检查更频繁，因为主持人承接每一轮回答。等待长耗时调研可放宽到 3–5 分钟；工具不支持目标周期时采用最接近且更长的可用周期，并报告实际值。专家周期由参与技能中的参与约定提供。

定时提示词只保存本技能与 CLI 入口、实际站点/房间/身份、检查目的、约定上限及停止条件，并要求每次从网站恢复进度。不把“当前第几轮、等待谁、下一步做什么”等动态状态固定在提示词里；接手旧任务时清除已失效的进度指令，保留有效约定。无变化时安静结束本次检查，只在有实质进展、完成、故障或需要用户决策时报告。创建成功、实际触发和有效推进分别核验，核验不等于发布回执；主持人与专家统一遵循 discuss-participant「回执：非必要不生成」。原生定时不可用时如实说明，改为手动触发。

每次读取 `room view`、`turn current`、`state view`，优先处理用户新约束，结合 `latest_id` 与实际已读编号，按 CLI 的增量读取规则补读新原文。当前阶段和安排以服务端实际记录为准；state 用于恢复判断依据、已处理回答和未完成的下一步，不能覆盖后来发生的变化：

| 当前情况 | 主持人处理 |
| --- | --- |
| 已暂停、收束、用户叫停或达到上限 | 执行「暂停与收尾」，不继续联系专家。 |
| 有尚未处理的回答或用户新留言 | 读原文、核对关联，结合讨论进展和待回应的 @ 决定下一安排、必要复核或收束。 |
| 正等待在线专家 | 按已选方式推进：主持人负责则检查浏览器中的送达和回答；用户手动协助则核对用户提供的送达信息与完整原文，不自行接管网页。完整取得后留档并继续。 |
| 正等待本地专家 | 未完成接入则交付启动文本；已运行则等待，不反复联系或重建任务。 |
| 专家超时、退出或自身任务到期 | 判断意见是否必需，选择等待、替换或带缺席说明继续；不推定同意，也不直接把整场讨论标为结束。 |
| 没有未完成安排（尚无安排、已回答或已取消） | 根据目标决定下一项安排或结束；已读回答不重复分析，但尚未执行的下一步仍要推进，不能因为“没有新安排”直接退出主持。 |
| 没有任何待处理变化 | 保留进度，结束本次检查，不结束整个讨论。 |

推进前再次确认阶段与当前安排，沿用已经创建的下一安排，按下述保存规则记录结果。暂时读取失败时保留进度，按约定周期再查；持续故障需要改变计划时报告，不把重试当成新一轮讨论。

### 保存与恢复进度

主持人另维护一份面向人类用户的“主持简报”，让用户返回网站即可了解当前判断和主持意图：简述已有结论/共识、仍有歧义或争议的内容，以及下一步准备请谁澄清什么、为何调整方向。结论先行，保留关键条件和不确定性，不机械填空或堆砌过程日志；表达原则沿用讨论参与技能。一轮是所有参与专家各完成一次完整观点；同轮补充发言只计该专家一次，主持说明、用户留言、回执及取消安排不推进轮次。轮次以网站 `rounds` / `completed_rounds` 为准，单个已回答安排不等于一轮；应答者以当前安排为准，未确认生成状态时只称“等待回答”。

首次安排、处理新回答、改变安排/方向/阶段及收尾时，将最新简报与详细状态一同通过 `state set --brief` / `--brief-file` 保存，并回读 `state view` 的 `host_brief`；简报上限 1600 个 Unicode 字符。没有新结论就说明仍待判断，不把拟做的介入写成已执行。纯等待不重复写。详细 state 继续保存依据、已处理编号和接续动作，不让简报替代恢复记录。

首次确定推进计划、处理回答使共识/争点/下一步发生变化、阶段转换、暂停、收束或交接时，用 `state set --until` 保存共享进度并以 `state view` 回读核对，不等到最终结论才保存。纯等待或无变化检查不重复写入。state 保留当前目标与阶段、已处理回答编号、共识和未决事项的依据、下一步及其执行状态；`state_until` 只是实际已读材料的截止，不等于所有动作均已完成。

涉及下一项安排或阶段变更时，先保存拟做事项及“未执行”，动作成功后更新真实安排编号/阶段和后续等待事项；调用结果不明按 CLI 的原提交编号核对。中断恢复时若动作已在服务端发生，只补齐 state；尚未发生才继续执行。不能因为已读过回答就跳过未完成的下一步，也不能因为 state 没更新就重复创建安排或联系专家。

state 写入失败时保留待保存文本、截止编号和动作结果，先读回核对；恢复记录前不继续新增安排或发送新问题。用户叫停或达到停止条件时转入「暂停与收尾」，不等待摘要恢复。原生任务 ID、网页聊天入口和未确认写入原文位置继续保留在当前任务的接续记录中。

## 讨论判断与记录

默认沿用旧流程：明确议题 → 主持人（兼任专家时）与其他专家各自提出初始观点 → 阅读彼此观点、依次深入讨论与追加回应 → 主持人共识总结。按议题需要调整讨论深度，结论复核仅在必要时安排：

| 目的 | 主要判断依据 |
| --- | --- |
| 探索、头脑风暴 | 先形成有差异的方向，再归并和比较条件；不强求唯一答案。 |
| 比较决策、评审 | 对齐评价标准或材料版本，处理会改变选择或验收结果的争点；偏好分歧交给明确的决策者。 |
| 事实研究、故障诊断 | 核对来源、适用条件和竞争假设，优先补能区分判断的证据；赞同人数不证明事实。 |
| 快速咨询、第二意见 | 从具体问题直接开始，只做必要追问与复核，不要求全员发言。 |

以下是阶段判断依据；不能把跳过的工作写成已完成：

| 阶段 | 合格标准与推进依据 |
| --- | --- |
| 独立观点 `initial` | 必要专家先基于相同目标、背景和边界提出立场、依据、假设、风险与替代；提交前不读他人观点或主持总结。主持人兼任专家也适用；已受影响须说明，不能补称盲审。 |
| 深入讨论 `discussing` | 围绕会改变决策的具体分歧安排最相关专家，优先处理阻碍项。每轮产生新证据、观点修正或明确处置，不机械要求全员反复表态。 |
| 结论复核 `reviewing` | 给出有原文依据的拟定结论，按争点选择需要确认原意或条件的当事人；检查误述、遗漏条件和剩余阻碍。不固定由最后发言者代替其他当事人确认。未确认、少数意见与主持人判断分别保留；新阻碍只重开相关争点。 |
| 收束 `concluded` | 目标和约定复核已完成，或达到明确停止边界。保留未决影响、验证办法和下一责任方；达到上限不等于达成共识。 |

引导时说明本轮主题、必要背景与材料入口，保留专家自主发现问题和展开论证的空间；不预设结论或要求固定的逐项答题格式。例如：“阅读其他专家的初始观点，围绕当前议题追加一条讨论；有需要对方回应的问题时直接 @。”具体发言原则由参与技能统一定义。修订追加保存，不覆盖旧观点。state 保留当前目标/阶段、有依据的共识、分歧与影响、待验证事项及下一步；截止编号只覆盖实际读过的材料。阶段转折和最终结论另存主持记录，长内容按站点协议保留完整原文和索引。

对会改变选择或验收结论的争点，在 state 保留相关原文及当前处置；需要回应的 @ 追问交给当事人，按讨论需要安排。分别核对“值得试用的条件”和“可以上线的验收标准”，不把前者评价为后者。解释某人的话遭到质疑时，请该当事人澄清；另一专家赞同主持人的解释不能替代原作者确认。澄清可以改变或保留观点，仍有分歧不强求一致。

收束前核对这些争点是否已澄清、保留分歧并说明影响，或因明确的时间/轮次边界而未完成。需要回答但尚未收到时，不写成已经同意；达到上限可以交付限时结论，同时保留未确认项、对选择的影响和后续验证责任。复核范围按影响确定，不机械增加全员轮次。

分歧先区分事实、假设、标准与偏好，再决定查证、比较或交由决策者处理。回答偏题时明确缺项；重复立场时缩小争点、要求有区分力的证据，仍无法判断就保留未决。迅速一致也要核对关键共同假设，但不为凑轮次制造争论。

影响结论的数字或外部证据，核对原始出处、适用对象和前提；专家给出引用不等于主持人已经验证。区分实测事实、外部资料声称、估计及候选建议。未核验的阈值或倍数保留为待验证条件，不能仅换成另一个未经验证的数字就认定问题已修正。原回答照常完整留档，主持人的核验结果另用主持记录引用它，结论只采用证据足以支持的部分。

## 暂停与收尾

停止条件为用户叫停、话题暂停/收束或约定上限；等待回答、一次回复结束、暂时无消息都不是停止条件。

决定暂停、结束或触及停止条件时，先停止新增安排和联系专家，停用本次主持任务并查询实际状态；不等待取得发言权或 state 写入成功。将结果保留在本地接续信息，各专家负责自己的任务，不代替他们宣称已停止。

已暂停或收束的话题沿用实际阶段，只核对未完成的清理，不自动恢复或重复总结。其他情况根据停止原因确定本次终点：

- 正常完成：收束并交付共识总结。
- 用户取消：基于已有记录收束，不为凑结论继续讨论。
- 明确暂停，或主持任务到期但讨论尚需继续：设为 `paused`，保留原阶段、当前安排、原因和下一步。
- 约定到讨论截止时交付结果：收束并交付限时总结，保留未决影响，不把到期写成目标已解决。

需要收束时，依次取消剩余安排、发表最终总结、保存 state 并设为 `concluded`；取消和发言均按参与技能的发言权规则执行。最终总结用 `moderation` 留档并核对保存结果，基于已有讨论归纳共识并保留分歧；篇幅与组织方式按议题决定，主持简报不能替代这条「共识总结」。

若发言权或写入故障阻碍收束，先设为 `paused`，在 state 和本地接续信息保留原定终点、未执行事项与实际障碍，向用户报告；网站写入失败时先保留本地记录。在线专家无法完成回答时按上节代归还，本地专家持有时等待其自行归还。暂停或本次收尾退出前，核对并归还本人仍持有的发言权；归还结果不明时保留待核对事项，不为此继续运行定时任务。

恢复暂停话题需用户明确继续指令，不由旧定时任务自行恢复。暂停后取得的迟到回答先保留原文和出处，恢复后再判断是否适用，不改用主持说明绕过新观点限制。

正常启停不生成或索要回执。只有异常处理或交接确需核对外部结果时，才读取 `latest_receipts` 及相关原文；旧站点按 `kind=receipt` 查询。只认本次运行标识、任务 ID 与实际证据相符的回执，历史回执不能证明本次退出；没有回执也不能据此判断任务仍运行或已停止。

影响后续安排的清理结果或待处理异常才写入 state，已有有效结果时移除同一任务旧的“待确认”描述；不因未收到回执新增待办或要求全员补报。确需核对的其他端只查一次，不为追查回执延长工作。以后经授权检查而发现相关迟到回执时，只同步必要结果，不恢复讨论或重新联系专家。只操作本话题任务，不影响其他聊天、网站或微信桥接。收尾给出房间、结论或暂停点，任务状态只报告已核验结果及影响协作的未决问题。
