# 自由协作主持

仅用于自由协作房间的主持人（任务 `role` 为 `host`）。成员的回答与提交方式见参与技能的自由协作一节。

## 请求类型

任务的 `request_purposes` 说明每条请求为何交给你：

- `route`：用户未点名的消息，或全体调度交回的原问题，由你回答或分派；全体调度未代办时仍须读取原文，再决定安排。
- `handoff`：你派出的成员都已结束（含失败），据结果决定下一步。
- `notice`：程序发现了要你处理的事，请求所在消息写明是什么：成员执行失败、依次派活某一棒失败、重试后的结果，或你上次要求的续跑。先读相关原文和 `room view`，再决定重试、改派、核实修正，或告诉用户需要他定什么。你已有待处理请求时，程序只把通知写进记录、不另建请求：处理任何请求时，新消息里作者为“系统”的通知同样要处理。成员改了同一文件不发通知，需要时看 `room view` 的 `free.conflicts`（“冲突”表示双方都用编辑工具写过，“可能冲突”表示无法确认是谁改的）。
- `all`：用户请全体成员各自回应一次，其他成员已同时收到；你只回答自己的部分，不加 `--to`。
- `goal_start`、`goal_continue`：用户开启了 Goal，按技能 [discuss-goal](../../discuss-goal/SKILL.md) 处理。
- `discuss_start`：用户发了 `/discuss`，等你补全讨论目标后开启讨论。消息带了文本时以原文为准，只整理措辞；没带时从最近对话提炼，提炼不出明确的讨论问题就不开启，直接回答并说明缺什么。开启：`run start ROOM --request 请求编号 --goal-file 草稿`，上限用房间默认值，你不设置。然后照常简短回答；之后程序会给你讨论主持任务，按技能 [discuss-session](../../discuss-session/SKILL.md) 的 [讨论主持](../../discuss-session/references/host.md) 安排发言。

先 `room view` 看成员与状态，再决定由谁处理。

任务若有 `scheduler_suggestions`，按其中的 `request_id`、`message_id` 先读原问题；`applied:false` 表示未自动生效，`actual_action:unverified` 表示动作结果尚未核验。需要依据时用 `state decision ROOM DECISION_ID` 读取 `decision_id` 对应的完整判断，再自行决定；“没有模型判断”或没有记录编号时，不假定模型已经给过建议。

## 派活

- 需要他人时在回答中加 `--to 显示名`（可重复，不能点名自己），写明各自负责的文件或模块；不需要他人时不加，本次即结束。显示名是 `room view` 中 `members[].label`（如 `Gemini`），正文称呼也用它，不写 `name`（成员 ID，如 `Antigravity`）。
- 派出的工作无论点名几位，全部结束（含失败）后都会交回你，由你接着安排或汇总。只点名一位、它的回答已足以直接给用户（简单问答、无需验收）时可加 `--no-handoff`（API 为 `no_handoff: true`），做完不再交回；失败仍交回你。要评审、验证或接着安排的不要加。
- 发现还要继续、但本次执行不便接着做时（如等成员的结果之外还要复查、分几步推进），回答加 `--continue 继续做什么`（API 为 `continue`）：房间没有其他进行中的工作时，程序再唤醒你一次。你下次回答不带它、或用户发了新消息，就取消。不要用它等用户回复；需要用户定的事直接在回答里问。它只管一次续跑；用户开启了 Goal 时由 Goal 负责空闲续跑，不必再加。
- 需要预先指定实现后的只读评审时，先读 `review roster ROOM`，再在派实现的 `message post` 中带 `--next-review NAME --review-scope 范围 --review-roster REVISION`；评审者不能是本批实现者。授权与实现任务同时保存，自动要求该批交回主持人。候选目前限程序启动的 Codex CLI；没有合格成员时读取结果给出原因。
- 收到 `review_handoffs` 时，先用 `review ready ROOM --batch ID` 读取完整委派、交付和报告，确认可交既定评审后用 `review advance ROOM --batch ID --revision REV --submission-id UUID --as 本人` 推进。只处理该批交接，其他请求继续完成；状态变化须重读，不能替换评审者或扩大权限。能力失效、额度不足、交付不完整等原因保留在读取结果和任务中。实际投递前本机复核只读权限与能力版本，失败撤销该次评审并交回主持人。
- 收到 `handoff` 后交给其他成员或汇总给用户；成员的回答已完整时只用一两句说明完成，不复述。
- 几位成员要按固定先后接力、后一位依赖前一位的结果（写完再审、实现后评审）时，派活加 `--sequential`，`--to` 按接力顺序点名：程序在每位答完后直接交给下一位，最后一位答完交回你，中间不唤醒你。走完一圈算一轮（中间各棒不另计）。派活正文要把每一棒做什么、按什么标准交给下一棒写清楚，后面的成员靠它和前一棒的回答工作。
- 某一棒有几位互不依赖、可以同时做的成员（如几位评审各审一类问题）时，把他们写成同一棒：第一位用 `--to`，其余紧跟着用 `--with`（如 `--to 写手 --to 评审甲 --with 评审乙 --sequential --loop`）。这一棒的成员同时开工，全部结束才交下一棒，下一棒能读到他们每一份回答；组里有人失败，接力停下交回你，用户重试失败的那位后接着走。并行的成员看不到彼此的意见，派活正文要分清各自管什么。
- 派活时想让某位成员同时开工、但不必等它（如评审期间让记录员先整理别的材料），加 `--detach 成员`（可重复，不能与 `--to` 重名）：它和这次派活一起开工，交回你或交下一棒都不等它；它做完不交回你，结果在房间里可读；失败时程序通知你。用在依次接力上时，它只随第一棒开工一次。撤回这次派活会一并撤回它。
- 要“改完再审、审到通过为止”时再加 `--loop`：每走完一圈，交回你的 `handoff` 带 `sequence.phase: checkpoint`。本圈最后一位（最后一棒是同时做的一组时，其中任一位）明确要求返工时，用 `sequence continue ROOM --request 该交接请求编号 --as 本人` 开始下一圈（程序直接接着走，你本次即结束）；认可、只剩可不采纳的建议、需要你或用户裁定时，不继续，直接验收或说明。开启智能调度时，它会先替你判断检查点，只有明确返工才自动开始下一圈，其余仍交给你；任务的 `scheduler_suggestions` 记着它的判断。`sequence view ROOM ID` 可读本圈各棒原文。每开始新的一圈算一轮，轮数用尽时循环停下，由用户决定是否继续。
- 要在接力中途停下来由你把关（验收一稿再交下一位），或只让中间一段循环（写 ⇄ 审到通过再交记录员）时，用检查点，均须与 `--sequential` 同用：`--checkpoint 成员` 在该成员那一棒结束后交回你（`sequence.phase: gate`）；`--repeat 成员=起点成员` 在该成员那一棒结束后交回你，作为循环检查点（`sequence.phase: checkpoint`），再来一圈从起点成员那一棒开始，起点不能早于前一个检查点。交回时 `sequence.gate` 给出 `repeat_from`（再来一圈从第几棒开始）与 `can_proceed`（后面还有棒）。处理：要返工就 `sequence continue … --request 交接请求编号`（循环检查点再来一圈）；认可并往下走就 `sequence continue … --proceed`（普通检查点不加 `--proceed` 也是往下走）；要结束接力、裁定或说明时不继续，直接回答。往下走和再来一圈各算一轮。带检查点的接力不能在右栏调整顺序。
- 用户只点名你（旁问，如问近况、是否卡住）时：读 `sequence view`、`room events` 与进行中执行的详情后直接回答，接力和循环照常进行。旁问里的新任务涉及正在接力的成员或同一批文件时，等接力交回后再派，或先撤回原派活；互不相干的可以马上派。用户发言会清除你之前的 `--continue`，仍需要就在这次回答里重新带上。
- 同一条用户消息最多推进若干轮（`room view` 的 `free.max_rounds`，0 为不限；本链已用与上限见 `free.chain_rounds` 的 `used` / `allowed`，`allowed` 为 null 即不限，用户可调）：你派一次活算一轮，依次接力一圈算一轮，`--continue` 的续跑也算一轮，成员做完交回给你汇总不另计；程序发现问题的通知不计轮数，到上限后照样交给你。到上限时你的下一次派活会被暂存、任务链停下，由用户决定继续或发新消息；你不能自己加轮。派活前先想清楚需要几位、几轮，最后一轮留给汇总。（上限防止 AI 之间无人值守地来回转交。）
- 已知整项任务所需轮数超过剩余轮数时（连写几集、多步实现加评审），在开始派活时带 `--need-rounds N --rounds-reason "…"`（N 为从这次派活起还需要的轮数，含最后汇总）：剩余不够时任务链立即停下，用户看到理由并一键批准差额后才发出这次派活，之后不再中途停下；够用时照常派出。不要在回复里让用户改上限或回“继续”，也不要建议超出 `need-rounds` 上限（100）的数值。

## 房间控制

任务有 `host_workflows: true` 时，房主为本房间打开了“主持人完整权限”：房间里出了问题、或推进需要的控制，你自己处理，不请用户代劳。命令都是 `<cli> launch host-control 操作 … --access-file <本次任务的 access_file>`，成员用 `--member`（成员 ID 或显示名）。

- **先诊断**：成员失败、卡住或结果异常时，先读原因再动手：`<cli> room events ROOM` 看写入与状态变化（你看不到私聊和消息正文，原文用 message 命令读），`<cli> execution view 执行编号` 看服务端详情与失败原因，`host-control details --execution 编号` 看该次执行的本机过程（命令、输出、改动）。
- **再恢复**：
  - 偏了方向或要补充：`steer --member 成员 --text 话` 向它进行中的执行插话；不需要打断时优先用它。
  - 卡住或做错：`stop --member 成员` 打断（之后到的请求留到它下一次执行）；`stop-all` 停止全部执行、请求与接力（讨论进行中时用 `discussion`）。
  - 偶发失败（网络、超时、软件崩溃）：`retry --execution 编号` 重试。
  - 模型限流或不可用：`model --member 成员 --model M [--effort E]` 换模型；Codex 等软件的 App 卡住时 `adapter --member 成员 --adapter ID` 切到同一会话的 CLI（成员空闲时才能切）。
  - 成员无法恢复：`remove` 后 `invite` 换一位。
  - 撤回自己派出的活（接力或循环停不下来、方向错了、用户改了主意）：`withdraw --message 派活消息编号`，接力或循环立即停下，未开始的请求取消，进行中的那一棒停止，不再交回你。
  - 收到“执行 #N 已 X 分钟没有新输出”的系统通知时，先 `details` 判断它是在跑长任务还是卡住，再决定等待、插话、打断或重试。
- **调整成员**：`invite --name 平台 [--access read|write] [--model M] [--effort E]` 用本机已配置的软件邀请（返回新成员名，本次执行里就能点名）；`away` / `remove` / `back --member 成员` 暂离、移除、请回；`access --member 成员 --access read|write` 调整项目权限；`label --member 成员 --label 显示名 [--description 描述]`。
- **推进**：
  - 发言顺序：先 `order` 读取当前顺序和 `revision`，再 `order --order 甲,乙,丙 --revision REV`，列出全部尚未发言的成员。
  - 讨论：先 `discussion` 读取状态和 `revision`，再 `discussion --do start --goal 目标 --revision REV`（上限用房间默认值）或 `--do pause|resume|end --revision REV`。
  - Goal：任务需要在房间空闲时持续自动推进、且目标和完成标准明确时，先 `goal` 读取状态和 `revision`，再 `goal --do start --goal 目标 --revision REV`（预算用房主默认值，你不能改）；`--do pause|resume|end` 控制。

- **兜底**：派出要跑较久的活（多集、多轮接力、循环评审）时，`checkin --minutes N`（5–120）让程序在房间还有进行中的工作时每 N 分钟给你一次“定时检查”，你据此确认没有卡住、跑偏或失败未处理；房间空闲、停止全部或换主持人后自动结束，`checkin --off` 提前关闭。定时检查要在你处理任务（有进行中的执行）时设置。另外，成员连续 10 分钟没有新输出时，程序会单独通知你。
- **主动发言**：不是房间派来的任务、而是你需要主动说明或派活时（如定时检查发现问题、用户在你自己的窗口里要你发言、你自己的执行失效后结果需要补交），用参与技能“主动发言”一节的 `message post … --proactive`，不必等用户开口；主持人的主动发言可以同时 `--to` 派活或 `--continue`。你自己失败的执行也可以用 `host-control retry --execution N` 重试。
- **你自己失败时**：程序会发一条提醒唤醒你一次（提醒本身再失败就不再唤醒，需用户处理）。先核对自己会话里的进展：已有结果就用 `--execution 原编号` 补交；没做完就接着做完再补交，或 `retry` 重试；是模型额度或模型不可用造成的，可 `host-control model --member 你自己 --model M` 换模型，下次投递起生效。最后用本次执行简短回复这条提醒。

`revision` 过期会被拒绝，重新读取后再提交。用户要求停下、换人或调整顺序时直接执行；你自己发现问题时先诊断再处理。每次控制都在回答里说明做了什么、为什么。以下仍由用户决定，需要时在回答里提出：对你自己操作或更换主持人，批准超出上限的轮数，项目权限高于可写或放行被拒绝的工具，改项目目录，撤回、回退用户的消息，私聊。你自己的执行失败由用户处理。

没有 `host_workflows` 字段，或你是 API 主持人（没有命令行）时，这些操作请用户在网页上做，或请用户在电脑上“成员与设置 → 协作设置”打开“主持人完整权限”。事件记录和执行详情不需要该开关，主持人都能读。

用户请成员分工改代码（定计划、实现、评审、整理文档）时，先读 [开发协作](dev-flow.md)。

## 工作流

本次任务有 `workflow` 字段时，本房间启用了用户的工作流。它像技能一样按需使用：`workflow.description` 是它的用途，请求与用途相符或用户要求按它做时才用，其他请求照常处理。要用时，本会话还没读过、或 `workflow.revision` 与上次读到的不同，才读 `workflow.skill_path`（API 主持人读系统提示中的工作流正文）；否则沿用已读内容。按它组织工作时，`workflow.members` 列出每张卡片现在由哪位成员担任、是否在场、项目权限；只点名在场的成员。`workflow.missing` 列出启用后才新增、还没有成员的卡片：本次要用到时，运行 `<cli> launch workflow-join --card 卡片ID --access-file <本次任务的 access_file>`（多张用逗号分隔），返回的 `members` 给出新成员名，本次执行里就能点名；API 主持人没有命令行，在回答里请用户在右栏点工作流的“刷新”。成员离开或被移除的角色不要自行请回，在回答里说明缺谁，不另找成员代替。工作流只带来做法和成员，不扩大你的权限。

本次任务（本地任务文件或 API 的 `task`）没有 `workflow` 字段时，不按任何工作流做事，即使会话里读过。

用户请你把本房间的做法存成工作流（或要你按某种分工新建一套流程）时，按 [workflow-creator](../../workflow-creator/SKILL.md) 技能做。任务有 `host_workflows: true` 时，房主已允许你自行保存并启用，不必等用户导入。

用户请你启用工作流库里已有的工作流（如“启用工作流「连载」（`novel-serial`）”）时：任务有 `host_workflows: true` 就运行 `<cli> launch workflow-adopt --id <工作流 ID> --access-file <本次任务的 access_file>`，程序在本房间启用它、邀请缺少的卡片成员（离开的请回），返回 `members`（卡片 ID → 成员名）和 `skill_path`；本次执行要接着按它做时读 `skill_path`，下一次执行起任务里有 `workflow` 字段，按上文使用。用户只说了启用、没给具体任务时，回答说明已启用和带来了谁即可。没有该字段，或你是 API 主持人（没有命令行）时，不能启用：在回答里请用户在电脑上“成员与设置 → 协作设置”打开“主持人完整权限”后再让你启用。
