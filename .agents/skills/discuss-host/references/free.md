# 自由协作主持

仅用于自由协作房间的主持人（任务 `role` 为 `host`）。成员的回答与提交方式见参与技能的自由协作一节。

## 请求类型

任务的 `request_purposes` 说明每条请求为何交给你：

- `route`：用户未点名的消息，或全体调度交回的原问题，由你回答或分派；全体调度未代办时仍须读取原文，再决定安排。
- `handoff`：你派出并要求交回的成员都已结束，据结果决定下一步。
- `all`：用户请全体成员各自回应一次，其他成员已同时收到；你只回答自己的部分，不加 `--to`。

先 `room view` 看成员与状态，再决定由谁处理。

任务若有 `scheduler_suggestions`，按其中的 `request_id`、`message_id` 先读原问题；`applied:false` 表示未自动生效，`actual_action:unverified` 表示动作结果尚未核验。需要依据时用 `state decision ROOM DECISION_ID` 读取 `decision_id` 对应的完整判断，再自行决定；“没有模型判断”或没有记录编号时，不假定模型已经给过建议。

## 派活

- 需要他人时在回答中加 `--to 成员名`（可重复，不能点名自己），写明各自负责的文件或模块；不需要他人时不加，本次即结束。
- 只点名一位成员时，它的回答直接面向用户；还要按结果安排下一步（如再交评审）时加 `--handoff`，它做完你会再被唤醒。点名多位时，全部结束后总会回到你汇总。
- 需要预先指定实现后的只读评审时，先读 `review roster ROOM`，再在派实现的 `message post` 中带 `--next-review NAME --review-scope 范围 --review-roster REVISION`；评审者不能是本批实现者。授权与实现任务同时保存，自动要求该批交回主持人。候选目前限程序启动的 Codex CLI；没有合格成员时读取结果给出原因。
- 收到 `review_handoffs` 时，先用 `review ready ROOM --batch ID` 读取完整委派、交付和报告，确认可交既定评审后用 `review advance ROOM --batch ID --revision REV --submission-id UUID --as 本人` 推进。只处理该批交接，其他请求继续完成；状态变化须重读，不能替换评审者或扩大权限。能力失效、额度不足、交付不完整等原因保留在读取结果和任务中。实际投递前本机复核只读权限与能力版本，失败撤销该次评审并交回主持人。
- 收到 `handoff` 后交给其他成员或汇总给用户；成员的回答已完整时只用一两句说明完成，不复述。
- 同一条用户消息最多推进若干轮（`room view` 的 `free.max_rounds`，本链已用见 `free.chain_rounds`，用户可调）：你派一次活算一轮，成员做完交回给你汇总不另计。到上限时你的下一次派活会被暂存、任务链停下，由用户决定继续或发新消息；你不能自己加轮。派活前先想清楚需要几位、几轮，最后一轮留给汇总。（上限防止 AI 之间无人值守地来回转交。）

用户请成员分工改代码（定计划、实现、评审、整理文档）时，先读 [开发协作](dev-flow.md)。
