# 接力与问题卡

主持人要派依次接力、循环、检查点、等用户拍板，或同时派多位、后台成员时读本页；请求带 `sequence`，或用户在问题卡上找你（`question.task`）时也读。基本派活与轮数上限见 [请求与派活](room.md)。

| 需要 | 写法 |
|---|---|
| 固定先后、后一位依赖前一位的结果（写完再审、实现后评审） | `--sequential`，`--to` 按接力顺序点名 |
| 改完再审、审到通过为止 | 再加 `--loop` |
| 中途由你把关一稿，或只让中间一段循环 | `--checkpoint 成员` / `--repeat 成员=起点成员` |
| 用户作为一棒亲自参与或拍板 | `--wait-user 成员` 或 `成员=起点成员` |
| 一棒里有几位互不依赖、可同时做 | 第一位 `--to`，其余紧跟 `--with` |
| 某位同时开工、但不必等它 | `--detach 成员` |
| 派活后你自己还要接着做、不等成员 | `--keep-working` |

`sequence view ROOM ID` 可读本圈各棒原文。

## 依次接力

程序在每位答完后直接交给下一位，最后一位答完交回你，中间不唤醒你；走完一圈算一轮（中间各棒不另计）。派活正文要写清每一棒做什么、按什么标准交给下一棒：后面的成员靠它和前一棒的回答工作。

**同一棒几位**（如 `--to 写手 --to 评审甲 --with 评审乙 --sequential --loop`）：这一棒的成员同时开工，全部结束才交下一棒，下一棒能读到每一份回答；组里有人失败，接力停下交回你，用户重试失败的那位后接着走。程序不保证同一棒的成员彼此看不到（后交的人可能读到先交的）；需要各自独立判断时，在正文里要求先写完再读别人的，并分清各自管什么。

**后台成员** `--detach 成员`（可重复，不能与 `--to` 重名）：它和这次派活一起开工，交回你或交下一棒都不等它；做完不交回你，结果在房间里可读，失败时程序通知你。用在依次接力上时只随第一棒开工一次；撤回这次派活会一并撤回它。

**自己接着做** `--keep-working`（API 不提供）：这条回答收为派活卡，本轮不要结束，直接接着工作，房间为后续工作另起一张卡；做完照常用本次凭据 `message post` 回答（可再派活）。派出的工作结束时以一条通知交回你，在你这次回答之后送达。不要先回答“我接着做”再结束本轮（后面的工作在房间里就看不到了）。不能与 `--continue`、`--sequential`、`--next-review` 同用。

## 循环与检查点

`--loop`：每走完一圈，交回你的 `handoff` 带 `sequence.phase: checkpoint`。本圈最后一位（最后一棒是一组时，其中任一位）明确要求返工时，用 `sequence continue ROOM --request 该交接请求编号 --as 本人` 开始下一圈（程序直接接着走，你本次即结束）；认可、只剩可不采纳的建议、需要你或用户裁定时，不继续，直接验收或说明。按工作流派活时照抄卡片规定的出口口径（如“需要返工 / 需要主持人裁定 / 可以采用”），不要改写成二选一。

- 开启智能调度时，它先替你判断检查点，只有明确返工才自动开始下一圈，其余仍交给你，判断记在 `scheduler_suggestions`。
- 给下一圈补充说明（返工要点、豁免卡片的某条规定、要求全文写进回答）时加 `--note-file 说明.md`：下一棒先读这条说明，上一棒回答仍在 `sequence.answer_id`，各棒的 `sequence.previous_pass` 列出上一圈的回答编号。不要为附带说明另起一次接力（圈次会重新从 1 数，与稿次对不上）。
- 每开始新的一圈算一轮，轮数用尽时循环停下，由用户决定是否继续。

检查点均须与 `--sequential` 同用：`--checkpoint 成员` 在该成员那一棒结束后交回你（`sequence.phase: gate`）；`--repeat 成员=起点成员` 在该成员那一棒结束后交回你，作为循环检查点（`sequence.phase: checkpoint`），再来一圈从起点成员那一棒开始，起点不能早于前一个检查点。交回时 `sequence.gate` 给出 `repeat_from`（再来一圈从第几棒开始）与 `can_proceed`（后面还有棒）。

- 要返工：`sequence continue … --request 交接请求编号`（循环检查点再来一圈）。
- 认可并往下走：`sequence continue … --proceed`（普通检查点不加 `--proceed` 也是往下走）。
- 要结束接力、裁定或说明：不继续，直接回答。
- 往下走和再来一圈各算一轮。带检查点的接力不能在右栏调整顺序。

## 等用户拍板

`--wait-user 成员`（或 `成员=起点成员`，与 `--sequential` 同用）用于用户作为一棒亲自参与或拍板（跑团时用户扮演一位玩家、写作时用户在几稿里选一稿）。该成员那一棒用 `question ask`（contract=handoff）交候选并出题，接力停下等用户回答，不交回你；用户回答后往下一棒走（写了起点就从起点那一棒再来一圈），答案交给下一棒先读，并从它起算新任务链。在派活正文里告诉那一棒要出什么题。

- 普通聊天、点名某人的消息都不推进；停止全部、撤回这次派活或取消问题会结束等待。
- 那一棒没出题时程序会请你补题一次：先 `sequence view` 取 `gate.revision`，再 `question ask --file`（JSON 里写 `gate`）。
- 最后一棒之后等用户须写起点。

## 问题卡上找你

请求带 `question.task` 时，用户在问题卡上找你：`recommend` 是请你先讨论并给推荐，`decide` 是交给你决定（`question.delegation` 是用户交托的范围）。先 `question view ID` 读题目、`version` 与说明消息（`explanation_message_id`），必要时派成员讨论，再二选一，这条命令就是本次请求的回答：

- `question recommend ID --version V --choice 题目=选项 --text-file 理由.md`：问题升为新版本，仍由用户确认。
- `question decide …`：视为回答，答案按原路由交回提问者或下一棒。

用户专有的授权（扩权、费用、批准轮数）不能代为决定，说明后引导用户走正式入口。用户在微信里回复问题通知、但回复不是选项编号时，`question.delegation` 就是那句原话：能明确对应到某个选项就代为选择（`question decide`），在理由里写明依据；含糊就在房间里追问用户，不要猜。
