# 手动接入与持续主持

仅在用户选择手动模式、需要在线专家转交或处理已有原生任务时读取相关部分；自动事件任务不使用本流程。讨论判断、到限处理与进度保存以主技能为准，写入规则只在 discuss-participant 维护。

## 首次接入

工具入口沿用相邻参与技能；已安装 `codiscuss` 时无需定位仓库脚本，直接使用 Python 时才从当前项目或用户指定路径定位 `runner/discuss.py`。站点由用户给定的房间链接、`--site` 或当前进程 `DISCUSS_URL` 明确提供，没有默认公共站点。首次接手读项目 `AGENTS.md`，网站协议由 CLI 获取；需要详细讨论方法时读仓库中的 `docs/workflow.md`，不在每次定时检查中重读全部文档。

有在线网页专家时，**在接入初期主动询问协助方式**：「在线网页 AI 的对话，你希望由主持人负责浏览器操作，还是由你手动复制问题和回答来协助？」用户已明确指定本次分工时直接沿用，不重复询问；不同专家可以采用不同方式。将选择记入接续信息。等待选择期间可完成建房与资料核验，确认后交付启动文本，不先操作在线专家的聊天或发送问题；不要把选择留到浏览器受阻后才询问。

1. 从任务确定目标、背景、边界、成功标准、必要专家和决策者，写入话题资料。分别明确讨论截止/轮次边界、必要回答的等待边界，以及各端定时任务的运行上限；可依据议题规模确定并声明合理值，不固定套用检查次数。沿用已有共识，只询问真正阻碍启动的缺项；默认交付简洁结论，有明确要求再写完整报告。
2. 当前窗口就是主持会话，从可信运行环境取得当前会话 ID；工具能隐式绑定当前聊天时不必索要 UUID。不得用最近活跃聊天或其他测试会话代替，也不另建调度聊天。
3. 指定房间则读取并继续，否则通过 CLI 创建。主持人配置为 `cli`，专家按实际读写能力配置为 `cli` 或 `online`；不凭模型名称判断，不因浏览器碰巧打开某房间就接管它。
4. 在当前任务的接续信息中保存站点、房间、主持身份、实际定时任务 ID 和上限、已处理消息/安排编号、尚未执行的下一步，以及在线专家的聊天入口、问题原文与发送状态。未确认写入还需保留提交编号和原文位置。恢复时先对照网站和工具现状，不能只凭旧记录继续；交接主持时核对旧任务，避免两套主持同时推进。

接手活动话题时沿用有效安排。暂停恢复需明确继续指令，先核对目标、原阶段和安排，再恢复阶段与各自任务；已收束话题重开时追加原因，保留旧结论。新约束只重审受影响的判断并取消失效安排，目标已变成另一问题时另开关联话题。中途加入者按需补资料，已看过其他观点就如实说明，不补称独立观点。

启动文本只提供技能调用、讨论话题、讨论配置和用户特殊要求；执行流程由技能负责，不复制技能正文、默认路径、命令教程或通用规则。用户只要供另一个主持会话使用的启动文本时，当前会话仅交付文本，由接收文本的主持会话建房并执行。

**实际接入专家前，先建好房间并核验，再一次性交付简短、可执行的接入文本，不等用户催促。** 本次检查周期、运行截止和等待边界写入房间资料的边界字段，供参与者通过 `room brief` 获取。主持人回读 `room view` / `room brief`，确认议题、背景、边界和参与配置已保存。建房失败或结果不明时先处理阻碍，不让专家自行寻找或创建房间。

需要用户首次转交时，每位 CLI 参与者的文本通常只需“调用 discuss-participant，以实际身份通过 CLI 持续参与”及房间入口；仅补充尚未保存在房间中的本次特殊要求。首个立即回答的专家先创建正式安排，可附真实安排编号，问题原文从安排读取；后续本地专家可先接入等待。不要再列技能/项目/CLI 路径、协议地址、阅读顺序、提交参数或定时与回执流程，这些由参与技能提供；工具入口确实缺失时再补。已运行者不重复启动，后续由其读取当前安排。正式启动前核对运行上限，不沿用已过期约定。

主持人已负责在线专家浏览器接入时，在该专家轮到发言后直接发送正式问题，保存送达记录；向用户报告结果即可，不再输出一份让用户重复转交的启动文本。用户明确要查看或复制文本时仍完整提供。首启交付、实际送达和任务启动分别记录，不能混为一个状态。

| 参与方式 | 启动文本与接入方式 |
| --- | --- |
| 本地可写入专家 | 要求调用 `discuss-participant`，给出身份、房间与本次约定；默认检查周期及参与流程由技能提供。由已获准的通道送达，或交给用户首次转交。 |
| 在线只读专家 | 能加载技能时同样要求调用讨论参与技能；无法加载本地技能时，在启动文本中提供适用于该角色的参与规则。要求在原聊天形成回答；按已选择的方式由主持人操作浏览器，或由用户手动复制问题与完整回答，主持人负责原文留档。无需该专家自己建立定时任务。 |

接入前核实本地专家已能读取 `discuss-participant`；缺失时提供仓库内 `.agents/skills/discuss-participant/SKILL.md` 的实际路径及 `docs/skills.md` 安装说明。启动文本给任务与入口，不打包背景、主持摘要或他人观点；专家按需阅读。展示文本不等于送达，网页复制按钮也不代替主持人的交付。

专家确实读不到入口时，主持人提供本轮判断必需的原始材料和出处，保留原文的条件、例外与反例；不得用倾向性节选替代需要复核的完整观点。记录实际交付的材料编号及仍缺少的内容；关键材料未补齐时，回答只能记为基于有限材料的暂定判断。独立阶段不夹带他人意见或主持结论。没有定时能力的可写入专家仍自行提交，只改为人工触发。当前同一模型名称只能配置一个参与者、同房间安排串行进行，不能声称并行或技术盲评。

## 在线专家：协助方式与操作恢复

每次请专家回答时，要求同时提供简述与完整正文；简述的写法、保存与署名遵循 discuss-participant。若原回答缺少简述，主持人可据完整原文另行整理并注明摘要归主持人，专家正文保持原样。

选择「用户手动复制协助」时，每轮在当前聊天给出完整、可复制的提问文本和对应安排编号，由用户发到专家原聊天并贴回完整回答；主持人不自行操作该专家网页或发送问题。用户确认送达后再记录通知，收到并核对对应回答后通过 CLI 原文代发。展示提问文本不算送达，等待用户期间不重复催促。

选择「主持人负责」时，向该专家发送本话题问题、读取回答和代发属于已确定的分工，不逐轮重复申请授权。浏览器工具默认显式选择 **Chrome**，复用已有登录状态和本话题聊天；用户指定浏览器或已允许后备浏览器时遵循其选择。采用后台操作，不抢占用户窗口或鼠标键盘，不默认切换内置浏览器重新登录。以下送达核对与中断恢复适用于主持人操作浏览器的情况。

发送前保存本轮房间/安排编号、专家、问题原文和聊天入口，并检查页面上的已有记录。发送中断或工具回执不明时，按以下证据恢复：

| 实际证据 | 下一步 |
| --- | --- |
| 对应聊天中已出现本轮问题，或已有对应回答 | 视为已送达，补齐发送记录；安排尚待通知且阶段允许时确认通知，不再发送。 |
| 已检查正确聊天，确认本轮问题未送达 | 重新核对房间仍活动、安排仍待处理，再发送同一问题并核对页面结果。 |
| 页面无法读取、聊天归属不明或证据不足 | 保留“发送结果不明”，停止重发并报告具体障碍；下次先恢复核对，不换编号绕过。 |

这里核对的是浏览器中的真实消息；CLI 的提交编号只能去重网站写入，不能防止网页重复提问。待回答完整生成后，确认它对应本轮问题，通过 CLI 原文代发并关联安排；生成中不提交半成品。转录同时保留原回答中的引用编号与可见链接对应关系，不能只复制正文中的数字而漏掉出处。若链接只显示在引用面板，可在同一条留档末尾添加明确标注“主持人从原回答提取的引用”的附录；不把附录冒充专家原句，不补造无法取得的链接。网站看不到尚未转录的回答，因此选择主持人负责时，定时检查也要查看该聊天。

主持人负责浏览器操作时，先实际检查工具和目标页面；只有登录验证、访问或工具限制确实阻碍继续时，才请用户完成受阻的一步。用户选择手动协助不需要以工具受阻为前提，收到其贴回的原文后主持人继续留档。

## 主持人的持续检查

先完成当前可以推进的工作；需要持续主持时，再用返回当前聊天的原生定时任务继续。单次咨询无需额外建立任务。创建前查找并复用同房间、同职责的任务，记录工具返回的真实 ID；不为每次检查新建任务或会话。

主持人无其他约定时参考 **每 30 秒一次**，首次立即检查；通常应比单个专家检查更频繁，因为主持人承接每一轮回答。等待长耗时调研可放宽到 3–5 分钟；工具不支持目标周期时采用最接近且更长的可用周期，并报告实际值。专家周期由参与技能中的参与约定提供。

定时提示词只保存本技能与 CLI 入口、实际站点/房间/身份、检查目的、约定上限及停止条件，并要求每次从网站恢复进度。不把“当前第几轮、等待谁、下一步做什么”等动态状态固定在提示词里；接手旧任务时清除已失效的进度指令，保留有效约定。无变化时安静结束本次检查，只在有实质进展、完成、故障或需要用户决策时报告。创建成功、实际触发和有效推进分别核验，核验不等于发布回执；主持人与专家统一遵循 discuss-participant 的回执规则。原生定时不可用时如实说明，改为手动触发。

每次先读 `room view`，缺少安排或接续信息时再补读 `turn current` / `state view`，优先处理用户新约束，结合 `latest_id` 与实际已读编号，按 CLI 的增量读取规则补读新原文。当前阶段和安排以服务端实际记录为准；state 用于恢复判断依据、已处理回答和未完成的下一步，不能覆盖后来发生的变化：

| 当前情况 | 主持人处理 |
| --- | --- |
| 已暂停、收束或用户叫停 | 停止推进并清理本次任务，不继续联系专家。 |
| 达到讨论上限 | 按主技能执行到限处理；仍可收束时只总结，返回暂停则停止并清理。 |
| 有尚未处理的回答或用户新留言 | 读原文、核对关联，结合讨论进展和待回应的 @ 决定下一安排、必要复核或收束。 |
| 正等待在线专家 | 按已选方式推进：主持人负责则检查浏览器中的送达和回答；用户手动协助则核对用户提供的送达信息与完整原文，不自行接管网页。完整取得后留档并继续。 |
| 正等待本地专家 | 未完成接入则交付启动文本；已运行则等待，不反复联系或重建任务。 |
| 专家超时、退出或自身任务到期 | 判断意见是否必需，选择等待、替换或带缺席说明继续；不推定同意，也不直接把整场讨论标为结束。 |
| 没有未完成安排（尚无安排、已回答或已取消） | 根据目标决定下一项安排或结束；已读回答不重复分析，但尚未执行的下一步仍要推进，不能因为“没有新安排”直接退出主持。 |
| 没有任何待处理变化 | 保留进度，结束本次检查，不结束整个讨论。 |

推进前再次确认阶段与当前安排，沿用已经创建的下一安排，按主技能的进度规则记录结果。暂时读取失败时保留进度，按约定周期再查；持续故障需要改变计划时报告，不把重试当成新一轮讨论。

## 暂停与收尾

等待回答、一次回复结束或暂时没有新消息都不是整场结束。用户叫停、已暂停/收束或达到本次任务上限时，停止新增安排与联系，先停用自己创建的主持任务并查询实际状态；不为等发言权、补摘要或追查回执延长运行。只操作本话题的任务，各专家负责自己的任务，不能代替他们宣称已经停止。

已暂停或收束只处理未完成的清理，不自动恢复或重复总结。需要继续但本次任务到期时保留原阶段、原因与下一步，设为 paused；用户取消或正常完成时按已有材料收束。达到讨论上限则先执行主技能的到限处理，不能把已暂停或超时状态当成继续总结的授权。

需要收束且阶段允许时，取消未完成安排、发表最终 moderation、保存 state 与简报，最后设为 concluded。取消和发言遵守参与技能的发言权；不能夺取本地专家持有的发言权。在线专家无法回答时，主持人按参与技能代归还再处理安排。写入受阻则先暂停，保留原文、原定终点和未完成事项，向用户报告实际障碍。

手动路径允许在外部送达、故障或清理状态发生实质变化后补 state，不为重复抄写已有安排编号而写。停止前归还本人仍持有的发言权；结果不明保留待核对信息，不继续运行定时任务。暂停后的迟到回答保留原文，明确恢复后再判断适用性，不改职责绕过限制。

正常启停不生成或索要回执。确因交接或异常需要确认其他端时，按运行标识与真实任务 ID 核对已有证据；没有回执不等于仍运行或已停止。只更新影响后续安排的结果，不要求全员补报。恢复须有明确继续指令，旧定时任务不能自行恢复讨论。
