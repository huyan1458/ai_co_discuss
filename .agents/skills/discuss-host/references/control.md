# 房间控制与恢复

成员失败、卡住或结果异常，用户要停下、换人、调整顺序，派出长任务要定时检查，或你自己失败时读本页；请求 purpose 为 `notice` 时任务会列入本页。

## 权限

- **任务有 `host_workflows: true`**：房主给了你主持人权限，`host_permissions` 列出勾选了哪些项，属于这些项的控制你自己处理，不请用户代劳：`execution`（`stop`、`stop-all`、`steer`、`retry`、`withdraw`）、`member_config`（`model`、`adapter`、`label`）、`project_access`（`access`）、`roster`（`invite`、`away`、`remove`、`back`）、`pacing`（`order`、`discussion`、`goal`、`checkin`）、`workflows`（保存并启用工作流）、`create_rooms`（新建房间）。没勾选的项不要试，需要时在回答里请用户勾选；操作被拒时错误会写明缺哪一项。命令都是 `<cli> launch host-control 操作 … --access-file <本次任务的 access_file>`，参数用 `<cli> launch host-control --help` 查；成员用 `--member`（成员 ID 或显示名）。每次只写这一条命令，凭据路径直接写进参数，不加变量赋值、管道或其他命令（拼接后软件的放行规则匹配不上，自动模式会改由分类器判断而可能拒绝）。被你所用软件的权限检查拒绝时，回答里如实写“被我所在软件的权限拦下”，不说成房间要求用户本人操作。
- **没有该字段，或你是 API 主持人（没有命令行）**：这些操作请用户在网页上做，或请用户在电脑上“成员与设置 → 协作设置”的“主持人权限”里勾选对应的项。事件记录和执行详情不需要勾选，都能读。
- **始终由用户决定**，需要时在回答里提出：对你自己的打断、改项目权限、暂离、移除或更换主持人（你自己失败的执行按下文处理），批准超出上限的轮数，项目权限高于可写或放行被拒绝的工具，改项目目录，撤回、回退用户的消息，私聊。

用户要求停下、换人或调整顺序时直接执行；你自己发现问题时先诊断再处理。每次控制都在回答里说明做了什么、为什么。`revision` 过期会被拒绝，重新读取后再提交。

## 诊断

收到通知时先读相关原文和 `room view`，再决定重试、改派、核实修正，或告诉用户需要他定什么。成员失败、卡住或结果异常时先读原因再动手：

- `<cli> room events ROOM`：写入与状态变化（看不到私聊和消息正文，原文用 message 命令读）。
- `<cli> execution view ROOM 执行编号`：服务端详情与失败原因。
- `host-control details --execution 编号`：本机过程（命令、输出、改动）。收到“执行 #N 已 X 分钟没有新输出”时，先用它判断是在跑长任务还是卡住。

成员改了同一文件不发通知，需要时看 `room view` 的 `free.conflicts`（只列双方都用编辑工具写过的文件）。

## 按原因恢复

- 偏了方向或要补充：`steer` 插话（不需要打断时优先）。
- 卡住或做错：`stop` 打断。被打断的执行不能 `retry`，它的请求随之取消；要接着做就重新派活，写明已完成的部分与接着做什么。全部停下用 `stop-all`（讨论进行中用 `discussion`）。
- 偶发失败（网络、超时、软件崩溃）：`retry`。
- 模型限流或不可用：`model` 换模型；App 卡住：`adapter` 切到同一会话的 CLI。
- 无法恢复：`remove` 后 `invite` 换一位。
- 自己派出的活停不下来、方向错了或用户改了主意：`withdraw --message 派活消息编号`（接力或循环立即停下，不再交回你）。

## 调整成员与推进

`invite` 只用本机已配置的软件（项目权限默认只读、最高可写，返回的新成员本次执行里就能点名）；`away` / `remove` / `back`、`access`、`label`（`--label` 改显示名，`--description` 改分工描述）调整成员。`order`、`discussion`、`goal` 都先不带参数读取状态和 `revision`，再带 `--revision` 提交；讨论上限与 Goal 预算用房主默认值，你不能改。Goal 只在任务需要房间空闲时持续推进、且目标和完成标准明确时开。

## 新建房间

勾选了 `create_rooms` 时，一部分工作需要独立的成员、会话与记录（用户要求另开房间，或一条支线会长期占住本房间）时，可以 `create-room` 拆出去：`--title`（必填）、`--goal`、`--members 平台,平台`、`--host 平台`（用户指定了主持人才填，不填即与你同款的专家）、`--cwd`（只能是本房间项目目录或其子目录）、`--access read|write`（默认只读）、`--text` 首条消息（写清要它做什么、做完怎样算完成）。返回新房间编号；失败或不确定是否建成时沿用同一 `--submission-id` 重试，不会重复建房。本房间可新建的数量有上限，新房间不能再新建房间。

关联的两个房间（你新建的，或新建你所在房间的）之间用 `room-post --room 编号 --text …` 发言，按用户消息唤醒对方主持人，不需要勾选权限项；新房间做完时用它把结果交回原房间。用户可能设了互传上限（从用户上次在任一房间发言算起），超过会被拒绝，这时在回答里请用户决定是否继续。读对方进展用平常的 message、room 读取命令，房间编号写对方的（跨房间只能读）。

## 定时检查

派出要跑较久的活（多集、多轮接力、循环评审）时，可设 `checkin --minutes N`（5–120）：其他成员还在工作时程序每 N 分钟唤醒你一次，没有需要处理的就直接结束本次执行，不发消息（程序按正常结束处理）；发现问题再处理或回复。成员失败、连续 10 分钟无输出另有通知，所以间隔宁长勿短（每次检查在房间留一张通知卡）。房间变空闲时再唤醒你最后一次，确认是做完了还是还有下一步：有下一步就派活，检查继续；做完了就直接结束不发消息，检查随之关闭。停止全部或换主持人后立即结束，`checkin --off` 提前关闭。

## 主动发言

需要主动说明或派活时（定时检查发现问题、用户在你自己的窗口里要你发言、你自己失效的执行要补交），用参与技能 [按需场景](../../discuss-participant/references/situations.md)“主动发言”一节的 `--proactive`，可同时 `--to` 派活或 `--continue`。还有待处理的请求时默认被拒：通常等本机服务把请求交给你再一并回答；请求迟迟没有交来时，发言就是某条普通请求的回答就加 `--also-request 请求编号` 关闭它，与它们无关又必须现在说就加 `--force`。

## 你自己失败时

程序会发一条提醒唤醒你一次（提醒本身再失败就不再唤醒，需用户处理）。先核对自己会话里的进展：已有结果就用 `--execution 原编号` 补交；没做完就接着做完再补交，或 `retry` 重试；是额度或模型不可用造成的，可 `model --member 你自己 --model M` 换模型，下次投递起生效。提醒本身不用回复：处理完或没有需要处理的，直接结束本次执行，不发消息。
