# 请求与派活

用于主持人（任务 `role` 为 `host`）处理没有 `discussion_request` 的请求：房间未开任何模式时、Goal 进行中时都是这里。回答与提交方式见参与技能的 [回答房间请求](../../discuss-participant/references/room.md)。

## 按需页

用到时才读。

- [接力与问题卡](relay.md)：依次接力、循环、检查点、等用户拍板、同一棒几位同时做、后台成员、派活后自己接着做；请求带 `sequence`，或用户在问题卡上找你（`question.task`）。
- [房间控制与恢复](control.md)：用 `launch host-control` 前必读（停下、插话、重试、换模型、邀请、暂离、移除、请回、调整顺序、定时检查），权限边界与用法都在那里；成员失败或卡住、主动发言、你自己失败也读它。
- [工作流](workflow.md)：任务有 `workflow` 字段，或用户要把做法存成工作流、启用已有工作流。没有 `workflow` 字段时不按任何工作流做事，即使会话里读过。
- [开发协作与评审](dev-flow.md)：用户请成员分工改代码，要预先指定评审，或任务有 `review_handoffs`。

## 请求类型

任务的 `request_purposes` 说明每条请求为何交给你。先 `room view` 看成员与状态，再决定由谁处理。

- `route`：用户未点名的消息，或全体调度交回的原问题，由你回答或分派；全体调度未代办时仍须读原文再安排。
- `handoff`：你派出的成员都已结束（含失败）。交给其他成员或汇总给用户；成员的回答已完整时只用一两句说明完成，不复述。
- `notice`：程序发现了要你处理的事（成员失败、某一棒失败、重试结果、你要求的续跑、定时检查、你自己失败），消息写明是什么，按 [房间控制与恢复](control.md) 处理。你已有待处理请求时，程序只把通知写进记录、不另建请求：处理任何请求时，新消息里作者为“系统”的通知同样要处理。
- `all`：用户请全体成员各自回应一次，其他成员已同时收到；先独立回答自己的部分，不加 `--to`。用户用 `@全体成员` 点名时，所有人答完后程序会再发一条 `notice` 请你汇总：读各成员回答，写共识、分歧与你的取舍，需要时再派活；回应很简单（如打招呼、报模型）时一两句收尾即可。
- `goal_start`、`goal_continue`：按技能 [discuss-goal](../../discuss-goal/SKILL.md) 处理。
- `discuss_start`：用户发了 `/discuss`。消息带文本时以原文为准，只整理措辞；没带时从最近对话提炼，提炼不出明确的讨论问题就不开启，直接回答并说明缺什么。开启：`run start ROOM --request 请求编号 --goal-file 草稿`，上限用房间默认值，你不设置；然后照常简短回答，之后程序会给你讨论主持任务。
- 用户只点名你（旁问，如问近况、是否卡住）：读进行中执行的详情（有接力时加 `sequence view`、`room events`）后直接回答，进行中的工作照常。旁问里的新任务涉及正在工作的成员或同一批文件时，等交回后再派，或先撤回原派活；互不相干的可以马上派。

## 派活

默认做法：在回答里用 `--to` 点名、写清分工，其余参数按需加；完整写法查 `message post --help-host`（普通 `--help` 只列成员能用的）。

- 需要他人时加 `--to 显示名`（可重复，不能点名自己），写明各自负责的文件或模块；不需要他人时不加，本次即结束。派活正文要能独立看懂：直接写要做的事、材料编号与完成标准，不写“同上”“见前文”。
- **主线与支线**：你安排的发言顺序（`--sequential` 接力）是主线；你或用户直接点名某位成员是支线，不占发言顺序，与主线并行。被点名的成员空闲时立即开始，正忙时排在它手上的工作之后、不打断；轮到它的主线那一棒时若还在做支线，主线等它做完再继续。用户直接点名成员不会唤醒你，也不交回你；任务的 `branches` 列出这些仍在进行的支线（成员、消息编号），派活前先读，避开它们正在改的文件。
- 派出的工作无论点名几位，全部结束（含失败）后都交回你。只点名一位、它的回答足以直接给用户（简单问答、无需验收）时可加 `--no-handoff`（API 为 `no_handoff: true`），做完不再交回，失败仍交回你；要评审、验证或接着安排的不加。它仍占住房间（用户未点名的消息要排队），不是后台；要后台做、不等它，用 `--detach`（见 [接力](relay.md)“后台成员”）。
- 本次执行不便接着做、但还要继续时（等成员的结果之外还要复查、分几步推进），加 `--continue 继续做什么`（API 为 `continue`）：房间没有其他进行中的工作时，程序再唤醒你一次；“进行中的工作”包括不交回你的成员（`--no-handoff`、`--detach` 派出的），它们做完之前不会唤醒你。派活后要自己马上接着做、不等它们，用 `--keep-working`（见 [接力](relay.md)）。你下次回答不带它、或用户发了新消息就取消，仍需要就重新带上。不要用它等用户回复（需要用户决定时见参与技能 [回答房间请求](../../discuss-participant/references/room.md)“需要用户决定时”）；Goal 进行中由 Goal 负责空闲续跑，不必加。

### 轮数上限

同一条用户消息最多推进 `free.max_rounds` 轮（`room view`；0 为不限；本链已用与上限见 `free.chain_rounds` 的 `used` / `allowed`，`allowed` 为 null 即不限，用户可调）。你派一次活、依次接力一圈、`--continue` 的续跑各算一轮；成员交回给你汇总、程序发现问题的通知不计，到上限后通知照样交给你。到上限时你的下一次派活被暂存、任务链停下，由用户决定继续或发新消息；你不能自己加轮。（上限防止 AI 之间无人值守地来回转交。）

已知整项任务所需轮数超过剩余轮数时（连写几集、多步实现加评审），在开始派活时带 `--need-rounds N --rounds-reason "…"`（N 为从这次派活起还需要的轮数，含最后汇总，不超过 100）：剩余不够时任务链立即停下，用户看到理由并一键批准差额后才发出这次派活，之后不再中途停下；够用时照常派出。不要在回复里让用户改上限或回“继续”。
