# 开发协作与评审

仅在你是房间主持人、且用户请成员分工改代码（定计划、实现、评审、整理文档），要预先指定评审，或任务有 `review_handoffs` 时读本页；派活规则见 [请求与派活](room.md)。

## 分工

怎么组织由你按任务判断。房间特有的几点：

- 用户未表示可以开始时不派实现。
- 共享工作目录不加锁：派活写明每位成员负责的目录或文件，并行的部分不让两人改同一文件。
- `room view` 的执行报告列有改动文件，交评审时可据此写明范围。
- 并行实现交回后看 `room view` 的 `free.conflicts`：列出的文件确实被两位成员在同一时段都改过；没列出不代表没有，成员用命令写的文件不在检测范围内。
- 同一问题反复不通过，或本链剩余轮数（`free.chain_rounds` 的 `allowed` 减 `used`；null 即不限）不够完成下一轮时，停下向用户说明分歧与现状。
- 向用户汇报时写明仍未验证的部分。

## 预先指定评审

- 派实现时就要定好只读评审：先读 `review roster ROOM`，再在派实现的 `message post` 中带 `--next-review NAME --review-scope 范围 --review-roster REVISION`；评审者不能是本批实现者。授权与实现任务同时保存，该批自动交回主持人。候选目前限程序启动的 Codex CLI；没有合格成员时读取结果给出原因。
- 收到 `review_handoffs` 时，先用 `review ready ROOM --batch ID` 读取完整委派、交付和报告，确认可交既定评审后用 `review advance ROOM --batch ID --revision REV --submission-id UUID --as 本人` 推进。只处理该批交接，其他请求继续完成；状态变化须重读，不能替换评审者或扩大权限。能力失效、额度不足、交付不完整等原因保留在读取结果和任务中。实际投递前本机复核只读权限与能力版本，失败撤销该次评审并交回主持人。
