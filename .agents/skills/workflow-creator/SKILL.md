# 创建工作流（workflow-creator）

工作流 = 一份给主持人读的 `SKILL.md` + 一组 Agent 卡片，存在本机服务目录 `workflows/<id>/`，一个文件夹就是一个分享单位。启用后，卡片对应的角色作为成员加入房间，每次执行时收到自己卡片的提示词；主持人像用技能一样按需使用它：每次任务都看到 `description`，请求与它相符时才读 SKILL.md 正文，读过且没改过就不重读。

工作流是“软”的：程序只校验、保存、加载和带来成员，不强制工序。主持人能不能按流程组织、各角色能不能做对，全靠这些文字，所以按 [提示词设计原则](references/prompt-design.md) 写。

## 先判断该不该做成工作流

适合：多人分工、会在不同房间或不同项目里反复用。不适合时直接告诉用户更合适的做法，不硬做：

- 单个角色的职责：存成专家预设。
- 只属于某个项目的事实（设定、路径、进度）：写进项目文档。
- 需要程序强制轮次和发言顺序：用房间的“讨论”。

## 流程

1. **弄清需求**：目标产物；有哪些角色、各自负责什么；交接顺序；谁可以改哪些文件；什么算验收通过；哪些做法已在房间里跑通过。能从房间记录或用户描述得到的不问，只问会改变设计的关键歧义。
2. **设计**：按下面“写什么、放哪里”决定 SKILL.md 和每张卡片的内容。
3. **按格式写**：见“格式”。流程定下后，照 SKILL.md 画一张示意图 `flow.json`（见“流程画布”）。
4. **校验并保存**：见“校验与保存”，按报错修正，直到通过。
5. **修改已有工作流**：先读现有文件，沿用同一 ID，优先局部调整；改了谁接谁、增删了卡片，就重画 `flow.json`，没有的补一张；保存后，启用它的房间从成员下一次执行起读到新内容；新增的卡片不会自动加入这些房间，由主持人用到时补齐，或由用户在右栏点工作流的“刷新”。

## 写什么、放哪里

| 文件 | 读者 | 写什么 |
|---|---|---|
| `SKILL.md` | 主持人 | 用途；开工前准备；每一步找哪个角色、交回什么、怎么验收；各角色共同遵守的约束；产物放在哪里（写成“读项目 README 找到……”） |
| `agents/<卡片ID>.md` | 该角色 | 角色立场、质量标准、本角色特有的做法和常见错误 |
| `flow.json` | 用户 | SKILL.md 流程的示意图：谁接谁、哪里交回主持人、哪里循环 |
| `workflows/<子工作流ID>/` | 主持人与子工作流的角色 | 主线之外按需使用的一套做法（见下方“子工作流”） |

- **同一条规则只写一处。** 流程、交接和输出格式写在 SKILL.md，由主持人派活时写进任务；卡片不复述流程。原因：之后用同一 ID 修订时只需改一处，两处都写迟早会对不上。
- **SKILL.md 自成一体**：只按角色的显示名、描述和产物路径说话，不引用卡片提示词的内容（API 主持人读不到卡片）。
- **可分享**：不写本项目的具体事实、本机路径或密钥；项目信息写成去哪里读。
- **只写验证过的做法**：用户直接给了分工、还没跑过的，按用户的分工写，跑过一轮后再用同一 ID 修订。
- **权限按职责最小**：只有需要改文件的角色给 `write`；同一份文件同一时刻只让一个角色改。
- 主持人不设卡片；主持人的职责写在 SKILL.md 里。
- **固定先后的接力写成依次派活**：几个角色按固定顺序接力、后一位依赖前一位的结果时（写完再审、实现后评审），在 SKILL.md 写明主持人用一次依次派活点名这几位（按接力顺序），需要“改到通过为止”时写成循环，由主持人在每圈结束时决定是否再来一圈；不要写成主持人每一棒都亲自转交。原因：程序会在每棒答完后直接交给下一位，主持人只在开头和验收时出场。几位评审排在同一圈时，按问题类型分工、各自的“必改”只限本类。互不依赖的评审写成同一棒并行（主持人用 `--with` 点名），这一棒全部审完才交下一位，循环检查点读每位的结论，任一位要求返工就再来一圈；他们看不到彼此的意见，SKILL.md 要分清各自管什么。后一位要参考前一位时排成串行，并让最后一位读完前面的结论后给出合并结论：循环只读最后一棒，不汇总会漏掉前面的返工。

## 格式

```
<id>/
  SKILL.md
  agents/
    <卡片ID>.md
  flow.json           流程示意图
  workflows/（可选）    子工作流，每个都是一份完整的工作流（不再嵌套）
    <子工作流ID>/
      SKILL.md
      agents/<卡片ID>.md（可选）  只在用这个子工作流时加入的角色
      flow.json（可选）           它自己的示意图
      scripts/ 等（可选）
  templates/ 等（可选）  主持人要用的模板、参考资料，只认文本文件
```

整个文件夹按 Agent Skills 的标准写：去掉 `agents/`、`flow.json`、`commands.json` 这几样平台扩展，剩下的仍是一个能直接用的技能，`workflows/` 下每个子工作流单独拷出去也能用。所以 SKILL.md 里写角色之间的关系（“两位同时审，循环到通过”“不用等它交回”），不写房间命令的参数，换成命令是主持技能的事。

### 子工作流

主线是启用后由主持人一集一集、一轮一轮推进的做法；子工作流是主线之外按需触发的另一套做法，比如检查成稿的 AI 率并优化、请几位专家代入主角视角试演一个场景。它和工作流写法相同：自己的 SKILL.md、成员卡片和示意图。用户可以在输入框打 `/` 点名要用，主持人也会凭它的 `description` 自己判断；主线某一步固定要用它时，在主线里写明“此处用子工作流 X”。

- 什么时候拆成子工作流：不是每轮都做、有自己完整的步骤、离开主线也说得通。每轮都做的步骤留在主线。
- `workflows/<子工作流ID>/SKILL.md` 的头信息：`name`（= 文件夹名，规则同工作流 ID）、`description`（必填，最多 500 字，写清做什么、什么时候用）、可选 `metadata` 下的 `label`（显示名）；正文最多 20,000 字。最多 10 个，不再嵌套。
- 它的卡片放在它自己的 `agents/` 下，格式与主线卡片相同；卡片 ID 在整个工作流里（含主线和各子工作流）不能重复。启用工作流时只请进主线卡片，这些卡片由主持人用子工作流时请进、用完请离。示意图 `flow.json` 也放在它自己的文件夹里，可以画它自己的卡片，也可以画参与其中的主线卡片（节点写主线的卡片 ID，不另建卡片）。主线的示意图用 `{"id": "sub_1", "type": "sub", "sub": "<子工作流ID>"}` 节点标出转去子工作流的地方；子工作流的示意图里不能再放这种节点。
- 它的脚本放在它自己的文件夹里（如 `scripts/`），在它的 SKILL.md 里按相对路径写；要给 API 成员运行，照常在根目录 `commands.json` 登记，路径写 `{workflow}/workflows/<子工作流ID>/scripts/…`。
- 工作流文件夹对成员只读：子工作流要积累的东西（知识库、缓存）写到项目文件夹或本机服务目录下，不写进自己的文件夹。
- 子工作流用文件夹保存（`workflow-save --dir`）或在工作流页编辑；粘贴草稿不带子工作流，用草稿保存时已有的子工作流原样保留。

### 登记命令（给模型 API 成员）

以 API 方式加入的成员没有命令行。某个角色需要自己跑检查脚本之类的命令时，在文件夹根目录放 `commands.json` 登记，脚本本身也放进文件夹（如 `tools/`），这样随工作流一起分享：

```json
{ "commands": [
  { "id": "state-check", "description": "检查作品状态账能否解析、引文是否对得上",
    "run": ["python", "-X", "utf8", "{workflow}/tools/状态检查.py", "{path}"],
    "path": "作品文件夹，相对项目目录", "access": "read", "timeout_seconds": 120 }
] }
```

- `run` 是程序加参数的列表，不经 shell，成员只能按 `id` 运行、改不了命令行。`{workflow}` 换成工作流文件夹，`{project}` 换成项目目录，`{path}` 换成成员传入的一个项目内路径；用了 `{path}` 就写 `path` 说明要传什么。
- `access`：`read` 只读文件，只读成员也能运行；`write` 会改文件，只给可写成员。按命令实际行为如实写。
- 不写本机绝对路径；程序名用各电脑都有的（如 `python`、`node`），脚本依赖写进 SKILL.md。
- 本地软件成员（Claude、Codex、Antigravity）有自己的命令行，不用登记；在 SKILL.md 里写清哪个角色用哪条命令、什么时候跑。
- 别人导入时要勾选允许才会带上命令；主持人的草稿不能增删命令。

`SKILL.md`：

```
---
name: novel-serial
description: 做什么、什么时候用，一句话，不换行
metadata:
  label: 连载小说
---
（正文，最多 20,000 字）
```

`agents/writer.md`：

```
---
name: writer
platform: Antigravity
label: 执笔
description: 一句话说明职责，不换行
project_access: write
---
（只发给这个角色的专属提示词，最多 4,000 字）
```

- **工作流 ID**（文件夹名 = SKILL.md 的 `name`）：小写英文和数字，可用单个连字符连接（不在首尾），1—40 位。`metadata` 下的 `label`（显示名）最多 32 字；早期写在顶层的 `label` 仍可读取，保存时移到 `metadata` 下。
- **`description`** 最多 500 字：写清做什么、什么时候用。主持人只凭它判断一条请求该不该按这个工作流做，写含糊了，该用时会不用、不该用时会套用。
- **卡片**：最多 30 张。`name` 是卡片 ID，等于文件名，只用小写英文、数字和下划线，最多 16 位。`platform` 是平台 ID：`Claude`、`Codex`、`Antigravity`、`DeepSeek`、`Qwen`、`Grok`、`OpenAI`、`Custom`（网页显示的 Gemini 写 `Antigravity`，自定义 API 写 `Custom`），须是本机已配置的软件，或已配置的模型 API（官方平台可按已保存的 API Key 加入；Custom 须先保存完整的本机 API 配置）。成员名由程序拼成 `平台-卡片ID`。
- **卡片可选字段**：`label`、`description`、`project_access`（read / write / auto / full）、`model`、`effort`。生图不是卡片字段：房间添加了生图卡片后所有成员都能画，卡片提示词写清谁负责出图即可。不用的字段直接省略；模型和强度省略即用本机默认值。接入方式、可执行文件、密钥不写进卡片，由各自电脑的配置决定。各角色挑哪个平台和模型，见 [给卡片挑平台和模型](references/model-selection.md)。
- 头信息只支持单行 `key: value`，以及 `metadata:` 下缩进一层的单行 `key: value`；不支持多行值和列表。
- 卡片正文留空时使用该软件的默认提示。

## 校验与保存

| 你在哪里 | 怎么保存 |
|---|---|
| 房间主持人，任务里有 `host_workflows: true` | 房主已允许你自建：把草稿写成一个文件（下方“草稿格式”，只用一段 `1/1`），放在任务的 `draft_directory` 下，运行 `<cli> launch workflow-adopt --draft <文件> --access-file <本次任务的 access_file>`。程序校验、保存、在本房间启用并邀请缺少的卡片成员（离开的请回），返回 `members`（卡片 ID → 成员名），本次执行里就能点名派活。只能更新本房间绑定的工作流；卡片权限最高 write。 |
| 房间主持人，任务里没有该字段 | 你不能保存。告诉用户：在“成员与设置 → 协作设置”打开“主持人完整权限”后，你就能自己保存并启用；用户打开后再按上一行做。 |
| 不在房间里，用户直接让你建 | 先在一个临时文件夹里按“格式”写好，运行 `codiscuss launch workflow-check --dir <文件夹>` 校验；用户确认后运行 `codiscuss launch workflow-save --dir <文件夹>` 保存进工作流库。同 ID 会覆盖原有工作流，覆盖前先告诉用户。 |

不要直接写入本机服务目录的 `workflows/`：那样会跳过校验和写入锁，格式错的文件会让启用它的房间读不到工作流。命令失败时按报错修正，不要绕过。

### 草稿格式

草稿把整个文件夹写进一段文本，用于 `workflow-adopt`：

```
<!-- workflow-part: 1/1 id: novel-serial -->
<!-- workflow-file: SKILL.md -->
（SKILL.md 全文，含头信息）
<!-- workflow-file: agents/writer.md -->
（卡片全文，含头信息）
<!-- workflow-file: flow.json -->
（示意图 JSON）
```

- 分隔行必须独占一行、从行首开始。说明文字只能写在第一个 `workflow-file` 分隔行之前；之后的内容都算文件正文，最后一个文件后面不要再加说明。
- 在回答里发草稿时，不要把整段包在 Markdown 代码围栏里。一条消息装不下（正文上限约 32,000 字）时拆成多条，最多 20 段，每条都带分段头 `序号/总数`，同一个文件不要拆到两条里。写成文件给 `workflow-adopt` 时只用一段。
