# 主持人派活分析（dispatch-analysis）

只分析主持人怎样分派工作，不分析 Jev 的消息路由或接力判断。不修改房间、设置、提示词或技能，不依赖源码仓库。

## 范围与数据

- 按请求的房间、时间范围和时区分析。统计页有附带范围时沿用。接口不按日期或文件夹过滤，按时间和可确认的房间范围筛选。范围无从确认时不要用全站样本代替。
- 现有读取命令为 `codiscuss room dispatches [--room ROOM] [--after ID] [--view messages|chains]`，沿 `next_after` 分页。消息视图有分工理由、执行与作废原因、改派、反馈、版本与历史快照。链视图有结束状态、作废消息编号、用户介入、未处理失败、按执行去重的 token 和主持人版本。
- 用 `codiscuss message view ROOM ID` 核对可访问的原文。房间已销毁时只引用留存快照，标明原文不可查。
- 若当前执行无权读取，可以分析用户提供的合法导出。说明数据缺口，不读取管理员凭据或换身份绕过权限。不用汇总数字猜测某条派活的得失。

## 审查反馈

默认做反馈审查。优先读 👎、改派、作废，以及主持人自行选人但未写理由的案例。核对用户原始要求、主持人当时可知的资料、派活、成员回答和用户纠正。区分分工偏差、成员执行问题和证据不足，不能仅凭执行失败认定派错了人。总结共性时给出支持与相反例子。

## 版本对比

只统计已结束且有派活的任务链。按主持人模型和已记录的 `package_version`、`prompt_hash`、`skill_hash` 分组。无法归属的跨版本链与未记录版本单列，不重复计算。每组报告范围、链数和用量覆盖率。少于 10 条链只列数字，任一组证据偏少、差异可由波动解释或任务明显不可比时不下结论。不把同时改变多个因素后的差异归因给某一个。

| 指标 | 口径 |
| --- | --- |
| 作废派活率 | `host_withdraw`、`user_stop_or_retract`、`user_rewind`、`failed` 的派活消息编号取并集，除以派活消息数 |
| 用户改派率（下限） | 识别到改派或带 `should_be` 的 👎，按派活消息去重后除以派活消息数。直接点名、完工后另派或未撤回的改派可能漏记 |
| 用户介入率 | 有停止、撤回、回退或改派介入的链数除以链数；未处理失败另列 |
| 失败派活率 | `failed` 作废派活数除以派活消息数；`retried` 不等于失败 |
| 无效 token 占比 | `voided_dispatch` 与 `failed` 的 token 之和除以全部 token；同时报 `with_usage / executions`，从消息视图汇总时按 `execution_id` 去重 |
| 👍／👎 | 只计实时记录，房间销毁后的留存快照另列 |

字段缺失或分母为零时标明不可计算。若自算指标与统计页口径不同，注明差异。

## 交付

用请求者的语言，在平台主理人对话中按参与技能的规则一次交付正文或报告附件。标注**主理人实际使用的模型**，无法核实时写“未记录”，不要用被分析的主持人模型代替。先列范围、样本、事实指标，再单列 AI 判断。每项判断附房间与消息编号，版本对比注明组别的链编号范围和支撑结论的代表消息。交付前核对编号和数字，证据不足就不下结论。
