# 小说 / 剧本连载

## 主线

每一集走一遍：

> 主持人下任务书 → 编剧提建议 → 写手写 ⇄ 批评家·人物、批评家·设定审（循环到通过）→ 主持人验收 → 记录员记账（和下一集的编剧同时做）

派活轮数按次数算：编剧 1 轮；写 ⇄ 审每走一圈（写手加两位批评家）算 1 轮，通常两圈；记账和下一集的编剧（或阶段通读）同一次派出，不另占轮；第 2 步用 `--continue` 等记账时多 1 轮。完整一集一般 3–4 轮，大纲每个阶段写完另加 1 轮通读（见第 6 步），开写前另加 1 轮构思（见第 7 步）；验收前单独派读者时，每次另加 1 轮。派活前看房间的连续派活轮数，不够就请用户调大。

分工的原则：**流程、交接格式和验收标准是定死的；正文怎么写交给写手。** 任务书和审稿意见只给处境、约束和问题，不替写手决定动作、画面和句子。原因：写手拿到的越像清单，正文越像对账说明书。

## 项目文件夹

每部作品一个文件夹。位置读项目 README 找到；没有就照本工作流 `templates/` 下的模板建（模板里每个文件都写了该填什么）。

```text
作品名/
  README.md     总纲：简介、人物、分阶段大纲、已写出的故事事实、用户决定
  世界.md       世界规则，以及每条规则落到纸面上的画面
  文风.md       作家人格、禁用词、正反样本、参考作品、用户标注
  状态/         作者用的账本，按系统分文件（见下）
  正文/         第01集_标题.md ……
```

| 文件 | 谁写 | 什么时候改 |
| --- | --- | --- |
| README、世界 | 主持人 | 开书时建；每集验收后补上新写出的事实、地点和规则 |
| 文风 | 写手起草，用户审定 | 用户标出好句或尴尬句时，主持人追加（见第 4 步） |
| 状态 | 记录员 | 每集定稿后 |
| 正文 | 写手 | 写集和修订 |

**状态文件夹**：账本按“游戏系统”分文件，一起读、一起改的放在一个文件，每件事只记一处：

| 文件 | 记什么 |
| --- | --- |
| 主角.yaml | 截至哪集、故事内日期与天数；身体（伤、病、倒计时）；技能；记账口径 |
| 物资.yaml | 库存（地点 → 物品：数量、状态、来自第几集）；重要器物、载具与能源 |
| 据点.yaml | 地点：钥匙、门锁、冷区暖区、能不能住、现在有谁 |
| 人物.yaml | 配角现在的状态、在哪、最后一次出场 |
| 线索.yaml | 悬着的线：埋于、现状、短证据 |
| 分集记录.yaml | 每集一段：得到、用掉、失去、看见、学到 |

旧作品若仍是单个 `状态.yaml`，照用；以作品 README 的文件分工为准。

开书时缺哪个文件就先补：世界、README 由主持人写；文风请写手起草；状态请记录员从已有正文建。补好的文件交用户审定，未审定的部分标“草稿”。

## 谁读什么

主持人派活时照这张表给材料，不让成员通读全部资料。

| 角色 | 读 | 不读 |
| --- | --- | --- |
| 编剧 | 任务书、README、世界、最近一集 | 状态账本细节 |
| 写手 | 文风、上一集、任务书 | 编剧建议原文、审稿历史；拿不准的事实可以查，不通读 |
| 批评家·人物 | 先只读本集正文；再读 README（人物、人物知道的、用户决定）和需要核对的前几集；任务书只用来判断问题出在写手还是上游 | 状态账本细节 |
| 批评家·设定 | 本集正文与附注、任务书、世界、状态、相关前集 | — |
| 读者 | 指定的正文，读到交稿附注为止 | 附注、任务书、世界、状态、审稿意见 |
| 记录员 | 定稿正文、状态 | 任务书 |

## 每一步

1. **任务书**（主持人派给编剧，要求交回）。写手只读文风、上一集和任务书，所以任务书要把本集用得到的东西从世界、状态、README 里摘出来放进去。用户举过的例子，先分清是打比方还是要照写：打比方的只取它的用意，转写成处境；明确要照写的进【定死的】。原因：例子原样写进去，写手会把它当成现成答案。派编剧时上一集的账可能还在记（见第 5 步），“手头状态”先按刚验收的定稿写，标“待核对”，第 2 步改写任务书时再对照记好的账本改正。原因：编剧按这份任务书出分场，空着会让他用上已经耗尽的东西。照这个格式写，三层分开：

   ```text
   第NN集《标题》任务书

   【定死的】只放用户或大纲已经定死的
   锁定事件：必须发生的事和先后顺序（没有就写“无”）
   禁止：……
   篇幅：约多少字
   保存：作品文件夹/正文/第NN集_标题.md

   【处境】是素材，不是清单，不必每样都用上
   位置：大纲第几阶段，这一集在阶段里承担什么
   人物此刻：想要什么、怕什么、误会什么、手里缺什么
   本集世界：要展开的那块世界（摘自 世界.md 的原文）
   手头状态：会影响本集选择的物资、伤情、技能、悬着的线（摘自 状态/ 里对应的文件；只写现状，不写本集会得到或用掉什么）
   档案方向：一件什么样的实物，往外推哪块世界（作品采用档案时）
   结束时还悬着：这一集收尾时仍没解决的压力

   【开放】由写手决定
   场景怎么排、从哪开始、停在哪、人物最后怎么想
   ```

   不写人物最后“得到或学到什么”，也不写对白、固定动作和结尾画面，不点名要用哪种写法（比如“写一场显出他是行家的戏”）。原因：点了名的东西，写手会当成作业专门演一段。

   **发出前自查**：主角此刻最自然的做法是什么？任务书要他做的事如果偏离了这个做法，前文有没有立住理由？没有就先改任务书；偏离来自用户已定的事，先问用户。任务书提到的旧事（谁做过什么、东西在哪）和已写的前集对得上吗？对不上先改。原因：毛病在任务书里，写手和批评家只能多花一整圈返工。
2. **编剧建议**：每集只调这一次。编剧交回后，先确认上一集的记账已经结束，核对它的检查结果（见第 5 步），再对照账本改正任务书里标“待核对”的“手头状态”；记录员还没做完，就在回答里带 `--continue`（写明等记账结束后改写任务书），房间空下来时会再唤醒你。主持人读完编剧建议，标明哪些采纳、哪些驳回，并对采纳的分场再问一遍“他为什么不……”。采纳的内容由主持人改写进任务书：真正不可少的事件进【定死的】，其余进【处境】，不要求写手按场次执行。编剧建议原文不转给写手。与任务书冲突的，以任务书为准。
3. **写 ⇄ 审**：主持人用一次依次接力、循环的派活：写手一棒，两位批评家同一棒同时审（`--to 写手 --to 批评家·人物 --with 批评家·设定 --sequential --loop`；以 API 方式主持时用 `parallel` 把两位批评家列为一组）。两位都审完才交回写手或检查点。
   - 写手初稿在回答里发全文（先存盘，见规矩）；修订时只改文件，回答里只汇报改了什么。
   - 两位批评家各管一类，“必改”只用于自己负责的那一类；越界的看法最多标“应改”。两人同时审，看不到对方的意见，偶有重复，由写手合并处理。
   - 每位批评家最后一行只给自己这一类的结论，三选一：
     - “需要返工”：自己这一类还有必改项没处理；
     - “需要主持人裁定”：写手对必改项给出不改的理由，或者改法要动任务书、设定、用户已定的事。写手对文风类意见行使风格主权，不算分歧；
     - “可以采用”：以上都没有。
   - 有任一位是“需要主持人裁定”，就先交回主持人，即使另一位要求返工：主持人裁定后，还有必改项就按第 3 步重新派一次同样的循环，把裁定写进派活正文，写手按它和两人的意见一起改（`sequence continue` 不发消息，写手看不到裁定）。否则任一位是“需要返工”，就继续下一圈；两位都“可以采用”，交回主持人验收。原因：要裁定的多半出在任务书、设定或用户已定的事上，先改正文只会白走一圈。裁定只写明读者需要明白什么、现在卡在哪，不规定由谁说出来、用哪句话：规定了，写手就会让人物把条件一条条念出来。
   - 写手报“失败”时，先看文件有没有存盘、改动有没有落地：已经存好的，不让写手重做，单独派两位批评家审；确实没落地的，再重派写手。
   - 两位批评家里有一位失败，接力会停下交回你：已完成的那位不重做，只单独再派失败的那位审同一稿；两份结论都齐了，再按上面的规则继续、裁定或验收。
4. **验收**：主持人读文件，对照任务书检查。通过后，把新写出的事实、地点、规则补进 README 和世界（世界里写进正文的候选条目改标“正文”）；没通过就写明问题，再走一次第 3 步。批评家判“可以采用”不等于免检：主持人验收时自己对照前几集，核对人物在哪、物件的来去、谁知道什么，以及他的行为和他知道的、想要的是否对得上。修订动了重要的对白或情绪戏、你拿不准读起来怎样时，验收前单独派一次读者（`--to 读者`，不放进写审循环）；读者读的时候，不派写手改这一稿。读者的报告不算返工：值得改的，由你写进下一次派活。

   用户读稿时标出的好句、尴尬句，主持人记进文风的“用户标注”。同类问题在 3 集以上出现，才把它升进“禁用词与句式”。原因：每标一次就加一条禁令，清单只会越来越长，写手会换成另一套固定说法。
5. **记账**：验收通过、补完 README 和世界、起草好下一集任务书后，用一次派活同时派出下一集的编剧和记录员：`--to 编剧 --detach 记录员`（以 API 方式主持时用 `detach`）。不用等记录员：编剧不读账本，两人互不影响；记录员做完不交回你，失败时程序会通知你。阶段的最后一集改为和阶段通读一起派（见第 6 步）。派记录员时写明作品文件夹，让它读定稿、更新状态。本工作流附带状态检查（`tools/状态检查.py`，依赖 PyYAML）：记录员改完账自己运行，改到全部通过再交回，回答里附最后一次结果。派活时把完整命令写给它：`python -X utf8 <本工作流文件夹>/tools/状态检查.py <作品文件夹>`（本工作流文件夹就是 SKILL.md 所在的文件夹）；记录员以 API 方式加入时，改为让它用登记的命令 `state-check`，path 填作品文件夹。记录员运行不了时由主持人跑。主持人在下一步改写任务书前（第 2 步，或阶段通读交回后）核对检查结果；记录员报出的“正文与状态不符”，由主持人决定改正文还是改状态。
6. **阶段通读**：大纲一个阶段的最后一集验收通过后，用一次派活派三位同时通读、记录员同时记这一集的账：`--to 批评家·人物 --to 批评家·设定 --to 读者 --detach 记录员`。通读只读正文，和记账互不影响。三位把这一阶段的正文从头连着读一遍（需要时带上前面的阶段），各交各的：批评家·人物交“他为什么不……”清单，即读者会追问、正文没立住的人物行为和生活常识；批评家·设定只查跨集对不上的事实，即人名、生死、地点、物件的来去、时间先后、谁知道什么；读者交连读下来的感受。原因：每集单独审时，没有人连着读，前后几集对不上的地方只有连读才看得见。阶段长（超过六集左右）时，中途可以加一次。主持人逐条裁定：只动本阶段正文的，记进待办，攒批派写手改；要改前面的集、设定或用户已定的事，整理成选项交用户拍板。用户拍板前不改。
7. **阶段构思**：每个阶段的第一份任务书之前做一次，开书时也做；阶段预计不到三集可以省。用一次派活请编剧和批评家·设定同时答（`--to 编剧 --to 批评家·设定`）：编剧说这一阶段人物要过哪几道坎；批评家·设定拿时间、物资和规则，去找这一阶段会撑不住的地方。两人都只列会影响本阶段关键行动的依赖，每条写三样：依据或假设、可能的矛盾、怎么处理（或者为什么可以先不管）。算不出来的余量、还没定的日期可以留白；正文没写过的数不让记录员补，由你决定怎么落。你把近几集任务书要用的记进项目的待办处，会改变故事走向的整理成选项问用户，其余自己定。原因：存粮够不够、路怎么走、谁来接手这类漏洞跨着好几集，单集审稿看不出来，写完一个阶段再改，要翻修整段正文和账本。推演出来的只是假设：采用前不当作约束写进任务书，也不因为表里有一栏就非填满不可。

## 规矩

- **先存盘再发**：回答一发出，本次请求就结束，后面来不及再保存。
- **推理写进附注，不进正文**：人物为什么这样选、情节为什么可行，写在交稿附注里，附注存在本集文件末尾。为了过审往正文里补解释，正是小说失去个性的主要原因。但附注只供核对，不替正文成立：读者只看得到正文，正文里看不出来的理由，照样算问题。正文缺不缺一句交代，只看一件事：不补它，人物的决定还成立吗、读者还跟得上吗？跟得上就不补。熟人说话只说半截、前文已经立住的规矩后面一笔带过，都不算缺。附注只留当前定稿的说明，对审稿意见的答复写在房间回答里。
- **审稿只指问题，不写替换句**：写清位置、问题、依据和改的方向；具体怎么写由写手决定。
- **只改自己负责的文件**：同一个文件同一时刻只有一个人改。不经用户要求不提交 Git。
- **账本和标注只给作者看**：状态文件里的数量、技能程度、线的状态，世界里的“候选 / 正文”标注，都不写进正文。写进去，小说就成了游戏面板。
- **小错攒批改**：验收、记账时发现的正文小错（数目、物件来路、称呼重名），不打断当前这一集，先记进项目的待办处（读项目 README 找），攒一批再派写手一次改。
- **改已写的集，先列影响清单**：用户意见、审稿或通读引出要改已经写定的集时，先列清楚哪几集要改、哪几集只查、哪些不动，以及牵涉的事实（谁在哪、东西的来去、谁知道什么），再按前后依赖分批走第 3 步；只停下依赖旧前提的续写。收尾时没解决的逐条写明：小错可以留到下一批，会让剧情不成立的不能留。原因：改一处前提会牵动后面好几集，现想现改容易漏，漏掉的会顶着“全部完成”留在稿子里。
- **候选不等于采用**：写手新补的设定，验收前只算候选。用户最新的明确要求优先于本工作流和既有设定；会改变方向的歧义，主持人先问用户。
